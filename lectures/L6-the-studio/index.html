Part One

Workflow or agent

Two ways to do the same job. What each costs, and when to use which.

Who decides the next step?

WorkflowA fixed path you draw in advance: which steps, in which order, and which branch to take on which value. The engine follows the drawing.
AgentA model with tools in a loop (Lecture 5). At run time the model reads what came back and chooses the next tool.

Both call the same 15 tools from Lecture 4. Only the chooser differs: your drawing, or the model.

Cost and time

The workflow makes no model call: the engine fills templates and calls tools.

Ask Rasoi reads the system prompt, all 15 tool schemas and the history on every turn, about six model calls per run, and needed Kavita's “yes” before it committed.

Both did the same tool work in Bahi. Engine time is milliseconds; the agent's time is the model thinking.

The rule of thumbIf someone must sign off the process itself, draw it. If they sign off each outcome, an agent with previews and approvals can do it.

When to use which

Two questions about the job.

Are the steps known? If the next step depends on what you find, a drawing needs a branch for every case. That is an agent's job.

Is the input a record or free text? A form gives fields; an email needs a model to read it.

Click each job at Rasoi.

Check yourself

1. Neha's goods receipt: workflow or agent?

Workflow. A form gives the PO and the count; the steps are always receive → read status → tell Kavita.

2. Both got the reorder right 10 of 10. Why prefer the workflow for it?

₹0 and milliseconds per run instead of about ₹1.18 and 26 s, one fixed path Rohit can sign off, and no “yes” needed from Kavita.

3. “Can we buy from Shakti Seals?” Why not a workflow?

Which lookups matter depends on each answer: not in the master, no certificate, §6.2. A drawing would need every branch in advance.

4. Where does a model belong inside a workflow?

Only where the input is free text or the steps open up: an LLM node to read an email, an agent node for a question.

Part Two

The anatomy of a workflow

Trigger, nodes, edges, data, branches, the approval wait, errors and re-runs. One part at a time, on Rasoi's jobs.

Seven parts

We take each one in turn. This is the map.

A trigger starts a run

TriggerThe first node. It decides when a run starts and hands the run its starting data.

Manual: the Run button. Schedule: every Monday 09:00. Event: stock falls below its reorder level. Form: Neha's goods-arrived form. Chat or email: a message comes in.

In the Studio the event trigger calls check_stock on its items. On a fresh Rasoi it fires for WHS-STD-01, 8,000 free against 12,000, and passes {item_code, free, on_order, reorder_level, cover_days} on.

Fig. 6. Five ways to start the same workflow. Event values from logs/templates_fresh.json.

A node is one step

NodeOne step with inputs and one output. A tool node calls one toolbox tool, as one named person.

“As one person” matters. "as": "NDESAI" acts with Neha's Bahi permissions, nobody else's: she can receive goods, she cannot approve a PR. Only "as": "RMEHTA" can sign Rohit's approvals.

The Commit switch is confirm: off, a writing tool only previews. A template never sets it.

One tool per activity is why this works

In Lecture 4 we wrapped Bahi's terse services into tools, one per business activity, with previews, keys and receipts.

Now each tool is one card on the canvas. A person can draw “raise the PR” without knowing the seven services behind it.

Drawn on raw services instead, the same job is dozens of nodes and every screen trap (PRD-05, GST18-INTRA) is the drawer's problem.

An edge says what comes next

EdgeA line from one node's exit (its port) to the next node. A node runs when an edge into it was taken.
  • 1out: the node finished.
  • 2true / false: a condition chose a side.
  • 3rejected: the approver said no.
  • 4error: the node failed; follow this edge instead of stopping.
"edges": [ {"from": "low", "to": "plan"}, {"from": "plan", "to": "nothing_on_order"}, {"from": "nothing_on_order", "port": "true", "to": "pr"}, {"from": "nothing_on_order", "port": "false", "to": "note"}, {"from": "pr", "to": "rohit"}, {"from": "rohit", "to": "po"}, ... ]

“Reorder when low”, from the Studio. A node is skipped when every edge into it has settled and none was taken; skipping flows downstream.

Templates carry data

Template{{nodes.pr.request_no}} in a field means: the request_no of node pr's output, filled in when this node runs.

Whole-field rule. A field that is exactly one {{ }} keeps the value's type: 269040.0 stays a number.

Text around it: each {{ }} becomes text in the string.

A small expression is allowed: {{ trigger.reorder_level * 3 }}.

A missing field is an error that names it.

Fig. 7. Real output of the PR node in our Diwali run. From logs/templates_fresh.json.

A condition picks a side

Condition nodeTests an expression on the outputs so far and leaves by true or false. Only that side runs.

Whistles: below reorder. The PR side runs.

Gaskets: 66,000 free against 30,000. The PR side is skipped; Kavita gets “fine”.

Every branch you draw is a case you thought of in advance. The case you did not think of has no edge.

Fig. 8. Stock values from check_stock on a fresh Rasoi, logs/probe.json.

The approval node is a saved wait

Durable waitThe run stops, is saved as a document, and holds nothing in memory. Hours or days later it is loaded and resumed from the same node.

It reads the document's real status from Bahi with order_status. APPROVED: carry on. WAITING: save and stop. REJECTED: the rejected port.

Rohit signs in his own inbox, as himself. The workflow never signs for him.

Fig. 9. The PR waits for Rohit; the run waits with it, as one JSON document in the run store.

When a node fails

A tool that returns ok: false makes its node an error, with the tool's own message and next step.

With an error edge drawn, the run follows it: tell Kavita, or try another way. Without one, the run stops, failed, and names the node.

A warning stops the run too, by default: PRD-05 is closed, so a PO there saves as Draft. A person should look.

Retry only what is safe to retry

The worst error: Bahi saved the PR, then timed out before it answered. The node sees a failure. The PR exists.

A retry asks again with the same arguments. Because the tool's key comes from the content, it finds the PR instead of raising a second one.

A time-out between pr_save and pr_submit is now handled inside the tool: it reads the PR back and submits it, so the first call already returns WAITING FOR APPROVAL. The retry finds the same PR.

Re-running must not double-order

IdempotentDoing it twice has the same effect as doing it once.

The key is a hash of what the document is: user, item, quantity, cost centre, date. Never a random uuid4(), or every retry looks new.

The workflow engine adds nothing here: it gets this for free because every write goes through the toolbox.

Fig. 10. Two runs, one key, one PR.

We ran every template twice on the same Rasoi

The second run found what the first made, or stopped. Nothing was ordered or received twice.

Read the Diwali row closelyThe PR, the PO and the release were all found (already_done). But the Tell Rohit node ran again (Diwali and Dealer rows): Rohit got the same message twice. A message has no idempotency key. Put a condition before it, or accept the repeat.

Check yourself

1. Node pr output has no po_no. What happens to {{nodes.pr.po_no}}?

The node errors with “nodes.pr has no field 'po_no'” and the run stops (or follows the error edge). Nothing empty reaches Bahi.

2. Why does an approval not just loop until Rohit signs?

He may take days; a loop dies with the process. A saved run survives restarts and costs nothing while it waits.

3. A condition's false side has no edge. What runs?

Nothing more: the true side is skipped, and the run ends done.

4. Who signs Rohit's approval in a workflow?

Rohit, in his inbox, with his own permissions. The workflow only reads the status.

Part Three

Models inside workflows

An LLM node to read what no tool can, and an agent node: your own agent, as one card.

The LLM node reads free text

LLM nodeOne model call: a prompt template in, text or a JSON object with the fields you named out.

Sharma Home Appliances emails for 4,000 spare gaskets by 12 November. No tool can read an email.

The model returns four fields. Everything after it is fixed: find the item, raise the PR, tell Rohit.

One model call, about 250 tokens. The model reads; tools do.

Fig. 11. The Studio's “Dealer email to order”, our run. From logs/templates_fresh.json.

Keep the model's job small

Three habits for an LLM node.

Name the fields

fields: ["item", "quantity", "need_by", "dealer"]. The engine checks every field came back, or the node errors.

Look it up after

The model says “5 litre silicone gasket”; find_item turns words into GSK-SIL-05L. Never let a model invent a code.

Decide the commit

The template commits (₹53,808, within Kavita's limit). In the notebook's version the PR node only previews, and a person commits what a model read.
Why it mattersA wrong extraction in a workflow repeats every time the email shape repeats. Small, checked outputs are what make it safe to run unattended.

The agent node: your own agent

Agent nodeInstructions in plain words + a chosen subset of tools + a model, running the Lecture 5 loop inside one node.

You choose the person it acts as, so it has their permissions.

may_commit off: every write it tries is forced to a preview, whatever the model asks.

max_steps stops a loop that runs away.

Check yourself

1. The LLM node returns quantity: "4,000" as text. What would you do?

Ask for a whole number in the prompt, and let the tool's schema check reject a string it cannot turn into an integer.

2. Agent node or LLM node for “read the dealer's email”?

LLM node: one call, fixed fields. Nothing to decide, so no loop.

3. Your agent node has may_commit: false and the model calls create_purchase_request(confirm=true). What happens?

The engine changes it to confirm=false: a preview. The switch wins over the model.

4. How is the agent node different from Ask Rasoi?

Same loop. You wrote its instructions, picked its tools and its person, and placed it in a workflow.

Part Four

Inside the engine

A workflow engine is a short loop. You write one in the notebook in about 80 lines.

Four steps, in a loop

  • 1Find a ready node: all inputs settled, one taken.
  • 2Fill its templates from the outputs so far.
  • 3Run it, through the toolbox, as its person.
  • 4Write the log; mark the edges its port leaves by.

Stop when nothing is ready (done), a node failed with no error edge (failed), or an approval waits (waiting).

Fig. 14. The engine, the toolbox below it, and the run store beside it.

The loop in code

From NB6's MiniEngine. The Studio's engine is the same shape, with more node types and a run store.

A run is a plain dict, so it saves as JSON.

The port decides which edges are taken; the next ready() skips the rest.

def run_until_pause(self, run): while run["status"] == "running": nid = self.ready(run) # 1. a node whose inputs settled, one taken if nid is None: run["status"] = "done"; break self.step(run, nid) return run def step(self, run, nid): node = self.node(run, nid) status, output, port, text = getattr(self, "run_" + node["type"])( # 2 + 3. fill, then run node, self.context(run), run["nodes"][nid]) run["nodes"][nid].update(status=status, output=output) self.log(run, nid, status, text) # 4. the run log if status == "waiting": # an approval: save and stop run["status"] = "waiting"; run["waiting_for"] = output; return if status == "error" and not self.has_edge(run, nid, port): run["status"] = "failed"; return # no error path drawn for e in run["workflow"]["edges"]: if e["from"] == nid and e.get("port", "out") == port: run["taken"].append([e["from"], e["to"], port]) def run_tool(self, node, ctx, rec): cfg = node["config"] args = fill(cfg["args"], ctx) # {{nodes.pr.request_no}} -> "PR/2026/04417" args["confirm"] = bool(cfg.get("confirm")) # the Commit switch, never a template out = self.toolbox(cfg["as"]).call(cfg["tool"], args) # as Kavita, Rohit or Neha return ("done", out, "out", short(out)) if out["ok"] else ("error", out, "error", out["error"])
