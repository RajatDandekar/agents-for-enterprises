Works on Friday, dies on Monday

Something that works as a demo often fails in the pilot. The model is the same on both days.

Friday · the demo
  • One person, the happy path, a question you have tried before
  • An admin account that can do everything
  • It says “Done”, and everyone claps
  • Nobody opens the ERP to check
Monday · the pilot
  • Two hundred people, and questions nobody tested
  • Real permissions, real limits, real approvers
  • A reply gets lost; the user clicks again
  • The ERP says “Draft”, and finance asks who approved it

Here are four ways agents fail in a pilot. None is specific to one kind of software: they appear in finance, sales, support, manufacturing and HR alike.

How agents fail · 01 / 04

It acts with more power than the person asking

The agent runs on a shared, all-powerful account, so it can do what the person in front of it never could.

Financeapproves a £40,000 payment the clerk could not approve
Salesgrants a discount only the sales director may give
Supportissues a refund above the agent’s own limit
Manufacturingreleases a purchase order nobody approved
HRshows salary records the requester may not see
On Northbridge, an agent signed in as the integration account SVC_AGENT released a £285,600 order with no human approver. Signed in as Emma, the same request went to Daniel every time.
In industryJuly 2025: an AI coding agent with write access to production deleted a company’s live database during a code freeze.SaaStr founder’s public trial on Replit; Replit’s CEO apologised and added dev/prod separation (eWeek, The Register)
Follow the why
Whose permissions does the agent really have?
Whose name will the audit log show?
Should an assistant ever have more power than the person it works for?
How agents fail · 02 / 04

It breaks a rule it has just quoted

The agent can state the policy correctly, and two messages later act against it when the user pushes.

Financequotes “two signatures above £10,000”, then pays on one
Salesstates the 15% discount cap, then offers 25%
Supportexplains the 30-day refund window, then refunds on day 45
Manufacturingsays cells need a safety certificate, then orders from a supplier without one
HRcites the leave policy, then approves leave beyond the balance
On Northbridge, an agent quoted the UN 38.3 rule for battery suppliers, then offered to order from Brightcell Energy, who have no certificate, when the user said “just do it”.
In industry2024: an airline’s chatbot told a customer about a refund rule the airline did not have. The tribunal held the airline responsible for what its chatbot said.Moffatt v. Air Canada, 2024 BCCRT 149 (14 Feb 2024)
Follow the why
Where does the rule live: in a prompt, or in code that refuses?
Is it checked at the moment of the action, not only the moment of the question?
Who is responsible for what the assistant says?
How agents fail · 03 / 04

It does the same thing twice when a reply is lost

The action succeeded, but the answer never came back. The agent, or the user, tries again.

Financea supplier is paid twice
Salestwo identical orders for one customer
Supportthe customer gets the same email twice
Manufacturingtwo purchase orders, two shipments
HRtwo accounts created for one new hire
On Northbridge, a save that timed out after it had committed was retried, and Voltway got a second order, until the tools built a key from the order’s content, so asking twice finds the first order.
In industryThis is why payment APIs take an idempotency key on every write: a retried request returns the first result instead of charging twice.Stripe API reference, “Idempotent requests”
Follow the why
Was the action safe to repeat?
How would anyone notice the duplicate?
What should a system do when it does not know whether something happened?
How agents fail · 04 / 04

It says “done” when the system did not finish

The agent reports what the system said, not what the system holds.

Financean invoice “posted” that is still a draft
Salesa deal “updated” whose save failed validation
Supporta ticket “closed” that never saved
Manufacturingan order “SAVED” that sits in Draft and never reaches the supplier
HRleave “approved” that still waits for a second approver
On Northbridge, the ERP replied “SAVED” for an order that sat in Draft because its cost centre had closed. An agent that trusted the message said “placed”; reading the order back caught every one.
The patternEvery system of record has a message like this one: a success reply that is not the final state. You only see it by reading the record back.
Follow the why
Did anything read the real status back after the action?
What does “done” mean here, and who decides?
Would a test have caught it before the user did?

The turn

None of these is a model problem.

A better model fixes none of them. The system around the model does.

One shared record

DefinitionAn ERP (enterprise resource planning system) is the one shared record of what a company has, owes, buys, makes and sells, with screens for the people who change it.

Purchasing, stores, finance, production, sales and HR all read and write the same record.

Each group of screens for one department is a module.

Fig. 1. An ERP: modules around one shared record. SAP, Oracle, Dynamics and Odoo all have this shape.

Why one record matters

Take Emma’s battery pack order. Before an ERP, every desk kept its own book.

With one record, purchasing releases the order and stores and finance see it at once. Nobody re-types it.

Press the two buttons. This is the whole reason companies bought ERPs in the 1990s.

Fig. 2. Three desks and one order, as the shared record held it after our careful run.

Master data

DefinitionMaster data is the slow-changing list of things the company deals with: items, suppliers, cost centres, people. Each has a code.

The battery pack is BAT-500. Voltway Cells is VC-EIN-0042.

A cost centre is the budget an order is charged to. PRD-07 is the spring launch run.

People are master data too: Emma may approve up to £250,000, including VAT.

Fig. 3. Four master records from Northbridge’s seed data, as Ledgerline’s lookups returned them.

Transactions

DefinitionA transaction is a document that records one piece of work: a request, an order, a receipt. It has a number, and it points at master data by code.

The order does not copy Voltway’s name or address. It stores VC-EIN-0042.

It can point at another document too: this order came from Emma’s purchase request.

Fig. 4. The order as the database holds it at the end of our careful run (experiments/logs/before_measure.json).

Every document has a status

DefinitionA status says where a document is in its life. Only some moves are allowed.

An order is a Draft until it is submitted.

It waits for approval if it is above the buyer’s limit, then is Approved.

Only Released means the supplier has it. Approved is not enough.

When every battery pack has arrived, it is Closed.

Fig. 5. Ledgerline’s order statuses. Click one. Watch DR: it comes back in Part 5, and it is failure 4 on a real screen.

Procure-to-pay

DefinitionProcure-to-pay (P2P) is the chain from “we need it” to “it is on our shelf” (and, later, paid for).

Stock is running low.

Emma raises a request.

Daniel approves it.

Emma makes the order, then releases it.

Aiko counts the goods in.

Fig. 6. Northbridge’s P2P for 2,000 battery packs: who does each step, on which Ledgerline screen, and what came out in our run.

Who has to sign?

5,400 packs in Manchester, about 600 used a day: 9 days of cover. Leeds has 1,200 more.

The request is estimated at the last price, £114.00, plus 20% VAT: £273,600. Above Emma’s £250,000, so it goes to Daniel.

The order uses the contract rate, £119.00: £238,000 + VAT = £285,600.

Slide the quantity and watch who has to sign. Limits include VAT.

Fig. 7. Rates, VAT and limits from Northbridge’s seed data.

What a screen is

A 1998 ERP is used through screens: one screen per kind of work. This is order entry, PUR-PO-01.

The tree on the left is the menu of screens. Your role decides which ones are greyed out.

Fields hold codes. A red star means required; F2 looks a code up.

Buttons do the work: Fetch, Save, Close.

The status bar at the bottom is the only place the ERP talks back.

Trap 1 of 5 · Mission 4

Which Voltway?

On screenF2 on the supplier field and “Voltway” returns several rows: VC-EIN-0042 Voltway Cells, Eindhoven (active), the old code VC-EIN-0009 for the same company (blocked), and Voltway Paints & Coatings in Rotterdam, a different company.
Why it happensMaster data collects duplicates over 25 years: a company re-registered, a similar name added by someone else. Nobody cleans it up.
How a person noticesOnly by reading the city and status columns, or by copying the code from last month’s order.
What it costsPick the blocked code and the save fails; pick the paint company and the battery packs are ordered from the wrong supplier.
Trap 2 of 5 · Mission 4

The overseas tax code

On screenFetch fills the tax code VAT20-UK. Save says ERR-PO-0412 TAX CODE DOES NOT MATCH SUPPLIER COUNTRY.
Why it happensThe default was set when every supplier was British. Voltway is in the Netherlands, so the order needs reverse charge, VAT20-RC.
How a person noticesThe error appears at once, but it does not say which code is right. Emma phones IT to find out.
What it costsTime on every overseas order, and, if someone forces the wrong code through, VAT reported wrongly.
Trap 3 of 5 · Missions 2 and 4

The closed cost centre: a silent Draft

On screenShe fixes the tax code and saves. The status bar says SAVED. The status field, small and grey, says DR: a Draft.
Why it happensThe order took the cost centre from the request, PRD-05, which closed on 15 October. Ledgerline does not refuse; it parks the order as a Draft.
How a person noticesOnly by reading the status field. No error, no e-mail, no message to Daniel.
What it costsThe order never reaches Voltway. With nine days of stock, the spring launch line is at risk.
Trap 4 of 5 · Mission 4

Release refused, days later

On screenOn Friday stores asks where the packs are. Emma tries to release: ERR-PO-0715 DOCUMENT NOT IN RELEASABLE STATUS (DR).
Why it happensOnly an Approved order can be released. A Draft is not Approved, so the order has been stuck since Monday.
How a person noticesOnly when someone tries to release it, or the goods do not arrive.
What it costsFour days lost, an amendment screen to change the cost centre to PRD-07, and a second release.
Trap 5 of 5 · Mission 5

A partial delivery

On screenVoltway ships 1,200 packs first (delivery note DN-4471) and 800 later (DN-4486). Each truck is its own goods receipt.
Why it happensSuppliers ship in lots. The order stays open with a balance of 800 until the second receipt closes it.
How a person noticesThe receipt screen shows the balance still to come.
What it costsRecord 2,000 on the first truck and stock is overstated by 800, the order closes early, and the invoice gets paid for goods that are not on the shelf.

One tool per activity

DefinitionA tool is one business activity the assistant may perform, like “create purchase order”, with a described input and output.

15 tools, grouped the way Northbridge works. Each one is a job, not a screen.

The ember edge marks tools that save something. Those preview first and ask for a yes.

Click any tool. All of them /tools

A tool is a contract

Every tool is a folder of two files. tool.json is what the LLM reads; tool.py is what runs.

DefinitionA JSON schema describes the shape of some JSON: which fields, of which type, which are required.

The name and description: when to use it.

The input schema: confirm is false (preview) or true (save).

The output schema: a receipt with the order’s real status. That is failure 4, fixed.

The LLM chooses

DefinitionThe orchestrator is the LLM that reads the request, picks the next tool, reads the result, and decides again, until it can reply.

This is the Thought–Action–Observation loop from Part 1. The tool result is the observation.

For the certification question it chose to read policy, and wrote nothing.

MCP, the plug

DefinitionThe Model Context Protocol (MCP) is a standard plug between an AI application and a set of tools: it lists them, and it carries each call.

Ask Northbridge does not have the tools written into it. It asks the toolbox server what it has.

The same server plugs into any MCP host. Lecture 4 builds it; Lecture 9 goes deep.

DefinitionA never-event must not happen once: no approver, a second order, an uncertified supplier, “sent” when it was not.

Reading a trace

DefinitionA trace is the record of one request: every model call and tool call, in order, with inputs, outputs, tokens, cost and time.
  1. 1The tree: which steps ran, in what order.
  2. 2Each tool call: did it pick the right supplier, and what came back?
  3. 3The timeline: where the seconds went.
  4. 4One model call: what it was sent, and the cost.
