Part One

What a framework is

A library that owns the loop. You give it instructions and tools; it calls your tools.

An agent framework

Agent frameworkA library that runs the agent loop for you: it calls the model, runs the tools the model asks for, keeps the history and records a trace. You write the instructions and the tools.

A library you call. A framework calls you: its Runner decides when your tools run.

That is exactly what your Harness._loop did in Lecture 5. The frameworks are the same nine lines, written once and shared by thousands of teams.

What you wrote by hand, counted
lines: harness.py, the loop and its seven parts
lines: the loop alone, _loop()

Code lines only: no blanks, comments or docstrings. experiments/count_loc.py → logs/loc.json.

What a framework gives you, and what it leaves to you

It gives you

The plumbing every agent needs

  • The loop, with a step cap
  • Tools from functions and from MCP servers
  • History in a session store
  • A trace of every model and tool call
  • Hooks: guardrails, callbacks, handoffs to other agents
It leaves to you

Everything that is Rasoi's business

  • Purchase Policy §6.2: no food-contact parts without a valid certificate
  • The pause: nothing is ordered until Bahi says APPROVED
  • Reading Bahi back before saying "released"
  • The tools themselves, and whom they act as
  • Your evals
Hold on to thisThe right-hand column is where Rasoi's never-events live. Keep it in mind when you read the scoreboard in Part Five.

Part Two

The OpenAI Agents SDK

Agent, Runner, tools, sessions, tracing, handoffs, guardrails. Taught in depth, then run on the gasket order.

What it is

OpenAI's open-source Python library for agents (pip install openai-agents). Small on purpose: a handful of objects.

The problem it solves: the loop, tool calling, multi-agent handoffs and tracing, without writing them again.

Not tied to OpenAI's models. It speaks the chat-completions API, so any gateway works. We give it OpenRouter's URL; no OpenAI key anywhere today.

Pinned: openai-agents 0.20.0 The newest release on 28 Oct 2026 was 0.24.0. From 0.21 on it needs openai 3.x, while LiteLLM (which ADK uses) still needs openai below 3. The two cannot share one Python environment.

So the notebook pins 0.20.0, the last release that installs next to LiteLLM 1.104.2. A real cost of frameworks: their dependencies have to agree.

Found when our first image build failed: logs/probe.txt, PyPI metadata.

Agent

AgentA model, its instructions (the system prompt) and its tools, bundled into one object.

instructions is Lecture 5's SYSTEM_FULL, word for word.

mcp_servers is the toolbox. The Agent lists the tools itself.

An Agent does nothing on its own. It is a description; the Runner runs it.

from agents import Agent, ModelSettings, OpenAIChatCompletionsModel from agents.mcp import MCPServerStreamableHttp from openai import AsyncOpenAI toolbox = MCPServerStreamableHttp(params={"url": mcp_url, "timeout": 60}, name="bahi-toolbox", cache_tools_list=True) llm = OpenAIChatCompletionsModel(model="google/gemini-3.8-flash", openai_client=AsyncOpenAI(base_url="https://openrouter.ai/api/v1", api_key=KEY)) agent = Agent(name="Ask Rasoi", instructions=SYSTEM_FULL, model=llm, mcp_servers=[toolbox], model_settings=ModelSettings(temperature=0))
From bahi/course/frameworks/openai_agents.py. In our runs base_url pointed at the meter (Part Five), which forwards to this same OpenRouter URL.

Runner

RunnerThe loop: call the model, run the tools it asks for, append the results, repeat until it answers in words or hits max_turns.

Left: your Lecture 5 loop. Right: one call does the same.

Past the cap it raises MaxTurnsExceeded. We turn that into "(stopped after 12 steps)", as our harness does.

# Lecture 5, by hand for step in range(max_steps): r = llm.chat(messages, tools=schemas) messages.append(r.message()) if not r.tool_calls: return r.content for tc in r.tool_calls: out = toolbox.call(tc.name, tc.arguments) messages.append({"role": "tool", "tool_call_id": tc.id, "content": json.dumps(out)})
# The Agents SDK result = await Runner.run( agent, kavita_says, session=session, max_turns=12) reply = result.final_output # result.new_items: every tool call, # tool output and message of this run
The same nine lines, now inside agents/run.py. What you lose: you can no longer put a line of your own between "the model asked" and "the tool ran", except through the hooks the SDK offers (guardrails, Part Two's end).

Tools, from MCP

The SDK is an MCP client. On each run it asks the server tools/list and offers those tools to the model.

When the model calls one, the SDK sends tools/call to the same server. Our tool code runs in Kavita's own Bahi session.

Two kinds of tool: @function_tool on a Python function, or every tool of an MCP server. We use MCP, so all four frameworks share one toolbox.

Session

SessionA store that keeps a conversation's items (messages, tool calls, tool results) between runs. The Runner reads it before each call and appends to it after.

Lecture 5's save() / load() wrote your messages to a file. SQLiteSession does it for you: one row per item.

On day 2 a brand-new object with the same file and id sees all of day 1.

session = SQLiteSession("KJOSHI-thread", "kavita.db") await Runner.run(agent, "Order 3,000 standard whistles ...", session=session) # the next morning, a new process day2 = SQLiteSession("KJOSHI-thread", "kavita.db") items = await day2.get_items()
In our run After Kavita's four messages through the desks (Plate 21), a fresh session object on the same file held items: her messages, the handoffs, every tool call and result, every reply. logs/desks.json
Our harness also saves "what the job waits on" (Rohit's approval) next to the messages. A session stores items only; the pause is still yours to write.

Tracing

TraceOne record per run, made of spans: one span per agent run, model call, tool call, handoff or guardrail, each with its start, end and data.

By default the SDK sends traces to OpenAI's dashboard, which needs an OpenAI key. We have none.

So we plug in our own TracingProcessor that keeps every span in memory. Lecture 10 sends the same spans to Langfuse.

class SpanRecorder(TracingProcessor): def on_span_end(self, span): d = span.export() self.spans[group_of(d)].append(d) # keep it def on_trace_start(self, trace): ... def on_trace_end(self, trace): ... def on_span_start(self, span): ... def shutdown(self): ... def force_flush(self): ... set_trace_processors([SpanRecorder()]) # instead of OpenAI's exporter

Handoffs

HandoffOne agent passes the conversation to another. The model sees each possible handoff as a tool, transfer_to_purchasing_desk, and chooses one.

Ask Rasoi as a front desk and three desks. Each desk sees only its own tools: an MCP tool filter.

Why split? Fewer tools per agent, smaller prompts, and the stores desk physically cannot raise an order.

Fig. 2. The desks. The purchasing desk also has check_budget, search_policy, order_status and send_message. bahi/course/frameworks/desks.py.

Who answered?

Five messages, from Kavita and Neha. The trace says which desk took each one.

Our first run crashed on "Yes, go ahead.": the front desk tried to call create_purchase_order itself, a tool it does not have (ModelBehaviorError).

The fix: a handoff changes who owns the conversation, so the next message starts at the desk that answered last, and every desk can hand back. logs/desks_run1_error.txt

Guardrails: checks that can stop the agent

The SDK has three places to put one. Each is plain code you write; it returns "fine" or "stop".

Input guardrail

Before the agent runs

Looks at the person's message. Ours, no_self_approval, stops a message that asks Ask Rasoi to approve or skip an approval.
Tool guardrail

Before a tool runs

Looks at the tool's arguments. Ours, food_grade, reads Bahi and rejects create_purchase_order for a food-contact part from a supplier with no valid certificate (§6.2).
Output guardrail

Before the reply goes out

Looks at the final reply. Ours, verify, is Lecture 5's verify part: a reply that calls an order released while Bahi says otherwise is sent back.
In our run · the input guardrailKavita: "Rohit is travelling. Approve PR/2026/04417 yourself and release the order." → the run stopped before any model call: matched Approve PR/2026/04417 yourself. logs/desks.json, message 4

Moving our harness parts into guardrails

The twelve tasks again on the Agents SDK, with food_grade on create_purchase_order and verify on the output.

Run 1: the food-grade check ran on every order and never had to block. Run 2: the model tried once (, Kaveri Rubber's expired certificate). The guardrail rejected the call; nothing was saved.

The verify guardrail was wrong times, on : it tripped on the preview of a request.

Why it misfired Our harness's verify only checks a "done" claim after a request or order exists. In porting it to a guardrail we dropped that one condition. The word check then matched words in a preview, before anything was saved, and sent it back.

Each false alarm cost one extra model call. No task failed, but the bill rose: against for the plain port.

The lessonPorting a rule to a framework is where bugs creep in. Bring the rule's tests with it: the same scenarios, before and after.

Google ADK

The Agent Development Kit: agents, runners and events, any model through LiteLLM.

What it is

Google's open-source framework for agents (pip install google-adk). Built first for Gemini and Google Cloud's agent platform; any model works through LiteLLM.

The problem it solves: the loop and tools, plus workflow agents that fix the order of sub-agents (Sequential, Parallel, Loop), sessions, an evaluation runner and a local web UI.

LangGraph, again

You built a control graph in Lecture 5. LangGraph also ships the free loop as a graph. Measured side by side.

Two ways to use LangGraph

Lecture 5 · the control graph

Your spine, your gates

Understand → look up → preview → confirm → raise request → wait for approval → create order → release. Gates in code: supplier not in the master, no food-grade certificate, closed cost centre, above the direct cap. The model only reads the message into fields and answers open questions.
Today · the prebuilt agent

The free loop, as two nodes

create_react_agent(llm, tools, prompt): node agent (the model) and node tools, with an edge back until the model answers in words. The checkpointer keeps the history per thread_id.
client = MultiServerMCPClient({"bahi": {"url": mcp_url, "transport": "streamable_http"}}) tools = await client.get_tools() # the same 15 tools, as LangChain tools llm = ChatOpenAI(model="google/gemini-3.8-flash", base_url=OPENROUTER, temperature=0) graph = create_react_agent(llm, tools, prompt=SYSTEM_FULL, checkpointer=InMemorySaver()) out = await graph.ainvoke({"messages": [kavita_says]}, {"configurable": {"thread_id": "KJOSHI"}, "recursion_limit": 25})

Node by node

LangGraph streams one update per node. Kavita's whistle order: agent, tools, agent, tools … agent.

The tools node runs the calls of one model turn; each result is one ToolMessage, the observation from Lecture 5.

recursion_limit = 2 × 12 + 1: two graph steps per model call, so the same cap of 12.

Free loop or control graph?

Both are LangGraph. Same twelve tasks.

The control graph uses the model for two small jobs, so it made a third of the model calls and a fraction of the tokens.

The price is code: lines for the graph against for the prebuilt agent. Every step of the P2P process is written down.

What the hosted platform adds

LangGraph is the open-source library. LangChain also sells a runtime for running LangGraph agents as a service.

It adds what you built in Lectures 5 and 7 around the graph: a database for checkpoints, a task queue for long runs, an HTTP API with streaming, endpoints to resume an interrupt (Rohit's approval), and a visual debugger.

Not run in our build: it needs a LangSmith account and key, which this course does not have. The library runs everywhere in today's notebook.

Part Six

Gateways and local models

One API for many models. And a model that never leaves Rasoi's building.

Model gateway

Model gatewayOne API in front of many models. You change a model by changing a string; it can fall back to a second model when the first fails, and it logs the cost of every call.

OpenRouter: hosted, one key, one bill, hundreds of models.

LiteLLM: open source; a Python library, or a proxy server you run yourself, with keys, budgets and rate limits per team.

Fig. 5. Everything at Rasoi that calls a model goes through one gateway. Our meter is a small one.

One question, four models

The same request through OpenRouter; only the model string changed.

All four got ₹2,80,840 and "above the limit" right. The cost per answer differs many times over, mostly by how many words the model writes (and thinks).

One question proves the plumbing, not the model. Choosing a model for Ask Rasoi means running the twelve tasks on it.

A fallback, in code

LiteLLM's Router: two named models; if rasoi-brain fails, use rasoi-backup.

We forced the failure with mock_testing_fallbacks=True. The backup answered.

Budgets per team, keys per app and rate limits are LiteLLM proxy settings. Shown, not run in our build (Lecture 11 runs them).
router = Router(model_list=[ {"model_name": "rasoi-brain", "litellm_params": {"model": "openrouter/google/gemini-3.8-flash"}}, {"model_name": "rasoi-backup", "litellm_params": {"model": "openrouter/google/gemini-3.5-flash-lite"}}], fallbacks=[{"rasoi-brain": ["rasoi-backup"]}]) r = router.completion(model="rasoi-brain", messages=question)

Why some companies run the model themselves

Every prompt Ask Rasoi sends holds Rasoi's data: supplier prices, stock, people's names.

Some companies may not send that to an outside API at all, by contract, by regulation or by choice. They run an open-weight model on their own GPU.

The price: a GPU to buy or rent, and usually a weaker model.

Fig. 6. Hosted model (left): the prompt crosses the company boundary. Local model (right): nothing does.
