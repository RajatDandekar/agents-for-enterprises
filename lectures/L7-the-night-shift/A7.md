# A7 · The Night Shift for your module

**Lecture 7, From Forms to Agents.** Due before Lecture 8 (demo day). Feeds the **operations (15)** line of the
/100 capstone rubric.

In class, Kavita's gasket order learnt to survive a lost reply, a two-day wait for Rohit, a dead worker and a
kill switch. Now give your module (`modules/` and `bahi/bahi/modules/<your_kit>/`) the same night shift.

## What to build

1. **A keyed main write.** Your module's main write service (`lv_save`, `tr_save`, `so_save`, ...) carries a
   `client_ref` whose value is a **hash of the document's content** (never `uuid4()`), and every write looks the key
   up (`<prefix>_list client_ref=...`) before writing and again after a timeout.
2. **Four failure drills, passing**, run with `bahi.durable.module_drills.run_module_drills(spec)`:
   | Drill | What happens | Passes when |
   |---|---|---|
   | D1 timeout after commit | Bahi saves, the reply is lost | exactly one document; record what the naive retry did |
   | D2 error before commit | "server busy" twice, nothing saved | exactly one document after the keyed retry |
   | D3 crash after commit | the process saves and dies; a fresh one retries | the retry finds the document by key |
   | D4 kill switch | writes switched off, then on | nothing written while off; one document after |
3. **Your module's waits.** Who approves your document, after how many hours you remind them, when you escalate and
   to whom, when you give up. Write them as a `WaitPolicy` and justify each number in one line
   (for example: leave for tomorrow cannot wait 24 hours for a reminder).
4. **A one-page runbook** for your module, in the shape of `deploy/runbook.md`: your ERP is down; an approval is
   stuck; duplicates appear (include the SQL that finds them in your module's tables); how to roll back.

## What to submit

- `modules/<your_module>/night_shift.py`: your `WriteSpec` (and, builder track, your workflow).
- `modules/<your_module>/drills.json`: the output of `run_module_drills(spec)`, from a run on Colab or Modal.
- `modules/<your_module>/runbook.md`: one page.
- Three sentences: what the naive retry did in D1 for your module, and why. (HR leave: Bahi refused the second
  save as an overlap, so there was no duplicate, but the naive client reported **failure** for a leave that was saved.)

## Checklist

- [ ] The key is a hash of content plus a `ref`; the same request gives the same key on two machines
- [ ] The write looks the key up first, and again after a `ServiceTimeout`
- [ ] Only retryable errors are retried (timeout, `ERR-SYS-0503`); every other refusal is reported, not retried
- [ ] D1, D2, D3, D4 pass; `drills.json` committed
- [ ] The receipt your tool returns is read back from Bahi, not taken from the save message
- [ ] The kill switch is checked before every write in your module's tools
- [ ] Your `WaitPolicy` numbers, each with a reason
- [ ] The runbook covers the four situations, with your module's duplicates query
- [ ] Builder track: the workflow history of one run (reminder fired, signal or poll, document released/approved)

## How it is graded (operations, 15 points)

| Points | For |
|---|---|
| 6 | Four drills pass (1.5 each), from your own `drills.json` |
| 3 | Keys from content, look-up before and after the write, retryable errors sorted correctly |
| 3 | The runbook: specific to your module, with the duplicates query, usable by someone who did not build it |
| 3 | Waits: a `WaitPolicy` with reasons (guided); a running workflow with a signal and two timers and its history (builder) |

Never-events still apply: a duplicate document from any drill scores 0 for that drill.

## Guided track (configuration)

Fill in a `WriteSpec`, run the drills, fill in the runbook template. Start from NB7 section 10:

```python
from bahi.durable.module_drills import WriteSpec, run_module_drills

def payload(s):                       # what your Save button sends; fetch a token first if your screen needs one
    tok = s.call("tr_fetch", itm_cd="GSK-SIL-05L", from_whs="WH-CHK-STR", to_whs="WH-PUN-LN5")["data"]["fetch_tok"]
    return dict(itm_cd="GSK-SIL-05L", qty=2000, from_whs="WH-CHK-STR", to_whs="WH-PUN-LN5", slot="NIGHT",
                fetch_tok=tok)

SPEC = WriteSpec(module="inv_transfers", user="GPAWAR", save_svc="tr_save", list_svc="tr_list", doc_field="tn_no",
                 payload=payload,
                 docs=lambda erp: erp.q("SELECT tn_no FROM tr_note WHERE itm_cd='GSK-SIL-05L' AND qty=2000 "
                                        "AND status NOT IN ('CN','RJ') AND created_on >= '2026-10-26'"),
                 content=("GSK-SIL-05L", 2000, "WH-CHK-STR", "WH-PUN-LN5", "NIGHT"))
report = run_module_drills(SPEC)
```

(The example is shaped like the inventory-transfers kit; check your own kit's services, fields and table names in
its `data-dictionary.md`.)

## Builder track (Python)

Also wrap your module's commit-and-approval path in a Temporal workflow, using `bahi/bahi/durable/` as the pattern:

- activities that look the key up before writing (`activities.py`), with the same error sorting;
- the approver's decision as a signal, read back from Bahi before acting on it; a poll for approvals made on the
  legacy screen;
- a reminder timer and an escalation timer from your `WaitPolicy`;
- run it under `WorkflowEnvironment.start_time_skipping()`, kill the worker once (`drills.crash_while_waiting` is the
  template), and submit the history (`runtime.history(handle)`) showing two worker identities.
