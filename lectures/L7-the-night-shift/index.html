Recovering when something hangs, waiting days for an approval, and running in production.

Before

Kavita checks, then retries

When Save hung, she opened the PO list to see whether it had gone through. When Rohit was travelling, she phoned him on Wednesday.
After

A durable workflow

Every write carries a key, so a retry finds the first order instead of making a second. The workflow waits days for Rohit, reminds him, escalates, and survives a crash.

What each side knows

Scrub through Kavita's Save. Bahi runs eight stored procedures and commits. The reply is lost on the wire.

Now the client and Bahi disagree. The client knows only that it stopped waiting.

Two ways on: save blind, or look the key up first.

Fig. 2. One run of drills.lost_reply(), timestamps and procedures as Bahi logged them. logs/lost_reply.json

“No reply” can mean three different things

1. Never arrived

The request died on the way. Nothing saved. Retrying is right.

2. Arrived and failed

Bahi said “server busy” before doing anything (ERR-SYS-0503). Nothing saved. Retrying is right.

3. Saved, reply lost

PO/2026/01182 exists, ₹2,80,840 is committed to PRD-07. Retrying blind makes a second order.

The client cannot tell these apart from where it stands. So it must not guess: it must ask Bahi, and it needs something to ask with.

Two promises, neither enough

At most onceNever retry. No duplicates, but a lost reply leaves the order missing, or saved and forgotten.
At least onceRetry until you hear back. Nothing lost, but a lost reply becomes a second order.
IdempotentDoing it twice has the same effect as doing it once. At least once, into an idempotent write, gives exactly one order.

The idempotency key

A value that travels with the write and is stored with the result. Before writing, look the key up; after a lost reply, look it up again.
po_save ... client_ref = "K4505F45939F0" # reply lost. Next attempt starts with: po_search client_ref = "K4505F45939F0" → PO/2026/01182 AP # found: do not save again

Bahi already has the column: po_hdr.client_ref. Every module kit has one too.

Where the key comes from

A random uuid4() is new on every attempt, so a retry can never find the first one.

In this course it would also change every prompt, and recorded model replies would stop replaying.

So the key is a hash of what the order is, plus a ref for two orders identical on purpose (the chat message id).

def order_key(o): parts = [o.user, o.supplier_code, o.item_code, o.quantity, o.cost_centre, o.need_by, o.rate, o.ref] blob = json.dumps(parts, sort_keys=True, separators=(",", ":")) return "K" + sha256(blob).hexdigest()[:12].upper() # bahi/bahi/durable/keys.py order_key(KJOSHI, DP-RJK-0042, GSK-SIL-05L, 20000, PRD-07, 2026-11-02, None, "msg-17") → K40B77AFC1F0C # run 1 → K40B77AFC1F0C # run 2 uuid4() → a new random value on every run, so a retry can never find run 1 workflow id = "po-" + key # a second start of the same order is refused
Fig. 3. Keys as printed by NB7 §3. The intent tool (Lecture 3) derives the same kind of key when the model gives none.

Three lines of logic

  1. Look the key up.
  2. Found: return it. Do not write.
  3. Not found: write, carrying the key. On a timeout, go round again; the look-up decides.

NB7 §4: two timeouts after commit in a row. The keyed write returned PO/2026/01182 on attempt 2; one order carries the key.

def create_order(self, o, request_no, t_h): # bahi/durable/activities.py s = self.erp.session(o.user) rows = self._call(s, "po_search", client_ref=o.key)["rows"] if rows: # an earlier attempt saved it return {**self.receipt(s, rows[0]["po_no"]), "found_by_key": True} self._guard(o.user) # kill switch, before any write rate, tax_cd, _ = self._price(s, o) f = self._call(s, "po_fetch", sup_cd=o.supplier_code, itm_cd=o.item_code, pr_no=request_no) saved = self._call(s, "po_save", ..., fetch_tok=f["fetch_tok"], client_ref=o.key) # ServiceTimeout -> retryable error return {**self.receipt(s, saved["doc_no"]), "found_by_key": False}

Duplicates, and the quieter failures

Redoing the job made a second order in 25 of 50 trials: 33 extra orders, ₹92,95,804 extra committed, 6,62,000 extra gaskets.

Pressing Save again never duplicated (Bahi's request rule), but reported 8 released orders as failed and left 9 saved orders unreleased.

The keyed workflow: 50 of 50 with exactly one released order.

Surprise: redoing the job duplicated even when the fault came before the commit, in 8 of 25 trials. The request and order from the first try had already been saved.

A chat turn cannot wait two days

Retrying one call is half of job 8. The other half is waiting for Rohit.

Where the wait lives today

In Kavita's head

She remembers the request, checks on Tuesday, phones on Wednesday. If she is on leave, the order waits with her.
Where it must live

Somewhere that survives

Not in a Python process: servers restart, deploys happen, laptops close. The wait, its timers and every step done so far must be stored outside the process.

Temporal does exactly this: it stores each workflow's history on a server, and any worker can pick the workflow up from there.

WorkflowOrdinary Python for the whole path: request, wait, order, release. Every step it takes is recorded.
ActivityA step that touches the world (Bahi). Temporal retries it on failure, on whichever worker is alive.
SignalA message into a running workflow: “Rohit has decided”, or “look again”.
TimerA durable sleep: “wake me in 24 hours”. It lives on the server, not in the process.
WorkerA process that runs workflow and activity code. Kill it and start another: same workflows.
HistoryThe list of events the server stored. After a crash the workflow code is re-run against it to rebuild its state.

So workflow code must be deterministic: it never calls Bahi, reads the clock or draws a random number itself. Those go in activities, workflow.now() and timers.

@workflow.run async def run(self, o: OrderRequest, p: WaitPolicy) -> dict: req = await self._write("raise_request", o, p=p) self.request_no, self.gross = req["request_no"], req["gross_value"] if req["status"] == "PA": # above Kavita's ₹2,50,000 self.stage = "waiting for approval" decided = await self._wait_for_approval(o, p) if decided is None: # 120 h, no decision await self._act("notify", o.user, o.user, ...) return self._done("expired") req = {**req, **decided} if req["status"] == "RJ": return self._done("rejected") po = await self._write("create_order", o, self.request_no, p=p) if po["status_code"] != "AP": # e.g. Draft on a closed cost centre return self._done("needs a person", receipt=po) rel = await self._write("release_order", o.user, po["po_no"], p=p) return self._done("released", receipt=rel)

Two days in one second

Temporal's test server jumps over timers. The request goes to Rohit on Monday 09:00.

Every 4 hours the workflow reads the request back: Rohit may approve on Bahi's own screen, and nobody signals.

24 h: remind Rohit.

48 h: escalate to Anand Patil, plant head.

50 h: Rohit approves. Order saved, released.

The signal wakes it. Bahi decides.

approval_decided

Sent by the app after Rohit approves with his own login. Bahi checks his limit and that he is not the requester. The agent never sends it for him.

recheck

“Look in Bahi now.” Carries no decision, so anyone may send it: the chat app, when Kavita says “Rohit approved it”.

a poll every 4 h

Rohit may approve on Bahi's old approval screen. Nobody signals. The workflow finds out anyway.

Whatever woke it, the workflow runs the request_status activity and believes only that. In the deploy smoke test, Kavita trying to approve her own request was refused by Bahi (ERR-SEC-0001), and the workflow did not move.

A changed word is a release

Every prompt, tool schema, the workflow and the model are pinned with a hash in versions.yaml. The image build fails if the code no longer matches.

The workflow is special: Temporal replays running workflows through the code deployed now. One that has waited two days for Rohit must still replay.

So workflow changes go behind workflow.patched("id"), or under a new name, with the old code kept until its workflows drain.

# deploy/versions.yaml (excerpt) prompts: toolloop_system: {version: 3, sha: 1788c5267119} tools: create_purchase_order: {version: 2, sha: 9b0950b31d02} release_purchase_order: {version: 1, sha: 6b3f601b1be1} workflow: PurchaseOrder: {version: 2, sha: 9bd7d5546cb4, task_queue: bahi-purchasing} $ python -m deploy.versions --check versions OK: every prompt, tool schema and the workflow match versions.yaml

Shadow: real requests, no writes.

Assist: only a person's Confirm writes.

Partial: a cohort first.

Full.

Above every rung, the kill switch. The workflow pauses; it does not lose the order.

Four situations, written down before they happen

First rule for anything that writes money: switch writes off first, investigate second.

Bahi is down

Leave the workflows: writes retry and look their key up. If it lasts, pull the switch so they pause instead of using up retries. Revive when /readyz is green.

An approval is stuck

Read the diary. Reminders are automatic (24 h, 48 h). Send recheck, never an approval on someone's behalf. At 120 h the workflow stops and tells Kavita.

Duplicates appear

Pull the switch. Run the duplicates query. Same key twice means a path that skipped the look-up. Cancel the extra in Bahi as its owner, not as the agent.

Rolling back

Prompt, tool, model: redeploy the previous image. Workflow code: patched or a new name, both kept until old workflows drain. Bad data: not a rollback.
