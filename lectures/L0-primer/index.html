One order, the whole course

Rasoi Steel Works, Pune, makes pressure cookers. It runs Bahi ERP 7.2, a form-based ERP from 1998.

Kavita Joshi, a purchase executive, must order 20,000 silicone gaskets before the Diwali run.

Done by hand in the sandbox, it takes eight screens, seventeen typed fields and two sign-ins. We will make it one sentence.

The form was doing nine jobs: asking for fields, knowing the route, looking things up, explaining rules, holding the draft, roles, proof, recovery, testing. Each lecture rebuilds some of them.

Everything here is fictional: the ERP vendor, the plant, the people, the suppliers and the numbers.

A reply is a dict

Bahi answers every request with the same envelope. On the wire it is JSON text; in Python it is a dict of dicts.

rc says whether it worked.

err_cd and msg explain a failure, tersely.

data holds the answer. Read it with env["data"]["on_hand"].

json.dumps / json.loadsTurn a dict into JSON text, and back. Our 210-character envelope survives the round trip unchanged.

How other systems reach Bahi

The legacy client, an n8n workflow and your agent all send the same thing: an HTTP request.

A method and a URL, some headers, and a JSON body.

The reply has a status code: 200 worked, 401 means you are not signed in, 504 means no reply in time. Toggle the token to see the 401 we got.

Fig. 3. One call to /svc/stk_query, with and without the token. Replies from our run.

Sign in once, then call

POST /login with a user and password returns a token.

Every service call sends it in the Authorization header. That is how Bahi knows the call is Kavita’s, and checks her role.

The same services the screens use are open to any program that signs in.

In Lecture 1 this matters: the agent will sign in as someone. Who it signs in as decides what it may do.

Fig. 4. Sign-in, a call, and a call without the token, as recorded in NB0.

BahiClient keeps the token

Writing headers by hand gets old. bahi/client.py signs in once and adds the token to every call.

It returns the same envelope you have already seen.

Exercise 2 reads Kavita’s last gasket order this way.

A company’s book of record

An ERP keeps what a company owns, buys, makes, sells and owes, in tables.

Master data changes slowly: items, suppliers, cost centres, users.

Transactions are business events written as documents: a purchase request, a purchase order. Each has a number, a header and lines.

Documents point at master data by code. People learn the codes by heart.

Codes are where people slip

Bahi has eight suppliers and five cost centres. Three rows are traps.

Deccan Polymers has two codes. The old one is blocked.

“Deccan Paints & Inks” is a different company with a similar name.

PRD-05, Kavita’s default cost centre, closed on 15 October.

Every document has a status

A purchase order starts as a Draft.

Above the raiser’s limit, it waits for approval.

Approved is not sent.

Only Released means the supplier has the order.

Some paths end: rejected, cancelled, or closed. Click a status to read it.

Fig. 6. Status codes of a Bahi document. The seed has 5 released orders and 1 waiting for approval.

Bahi enforces the moves

You cannot release an order that is still waiting for approval. The service refuses, with a code.

But not every rule is a refusal. Some outcomes are silent, and the code alone will not tell you something went wrong.

That is where Lecture 1 begins.

Messages in, text out

A language model reads a list of messages and writes the next one. That is all it does.

Text is cut into tokens, pieces of words.

You pay per token in and per token out, and you wait for each one written.

TokenThe unit a model reads and writes: roughly four characters of English. Our eight-word question was 11 tokens.
Fig. 7. Our first recorded call, with its real token counts, seconds and cost.

From tokens to rupees

Each model has a list price in dollars per million tokens, one for input and one for output. The course fixes ₹88 to the dollar.

Multiply, add, convert. NB0 exercise 4 writes this function.

One short call costs a fraction of a paisa. An agent that re-sends a long conversation many times does not: drag to 1,00,000 tokens in.

A smaller model, a smaller bill

We asked both tiers the same question, once each.

The small model answered faster and for about a seventh of the price.

On a one-line definition the two answers are equally good. On Kavita’s order they will not be equally good, and neither will be good enough alone.

Fig. 8. Seconds, ₹ and tokens per call, measured in NB0 (one call each).

It only knows what you send

Asked for Kavita’s approval limit, the model cannot know it. It says so.

Put Bahi’s own user record in the messages and it answers correctly. The extra 90 tokens are the fact.

Context windowEverything the model can read in one call. An agent is mostly code that decides what goes into it.

The model asks; your code acts

We describe one tool: Bahi’s stock enquiry.

The model does not run anything. It writes a small JSON request and stops.

Our code runs it against Bahi, as Kavita, with her permissions.

The result goes back as a message.

Now the model can answer with real numbers.

What the model sees of a tool

Not code. A name, a sentence, and the fields it takes.

The description decides when the model reaches for it.

The fields decide what it must fill in.

Bad names and terse descriptions make bad tool calls. Lecture 3 is about writing good ones.

Put it in a loop: an agent

Model, tool call, our code, result, model again, until the model answers without a tool call.

That loop is a few dozen lines of Python. You write it in Lecture 1.

Then we give it every Bahi service as a tool and Kavita’s six hardest requests, and watch what a model alone gets wrong.
