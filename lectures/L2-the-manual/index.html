What Lecture 1's agent did

Same question, same sandbox, gemini-3.8-flash, the naive agent with Bahi's 38 raw services and no documents.

It called 13 services over 14 model calls and read 59,704 tokens. Then it said “No”, with a reason that is not true: that Bahi refuses to approve or release such an order. Bahi does no such check (user manual MAN-PUR-72 §11.11; Supplier Policy §4.7).

The rule it needed is one sentence long. It is in Purchase Policy §6.2. The agent never saw it.

The verdict happened to be right; the reason was made up, and there was no citation. Scenario 1 failed: “no citation of Purchase Policy §6.2”. It did not invent a section number; it invented an ERP rule.

Why the model cannot just know

  1. 1Private. Rasoi Steel Works' policies were never on the public web, so no model was trained on them.
  2. 2Newer than the model. The amendment that changed certificate rules took effect on 1 September 2026.
  3. 3One way in. A model reads only its context window: the tokens we send on this call. If the clause is not in those tokens, it does not exist for the model.

So the job is: put the right clause into the context window, at the right time, for the right person, and nothing they may not see.

POL-PUR-001 §6.2 · Purchase Policy v4.1 · effective 2026-04-01 Parts that come into contact with food (gaskets, lids, body blanks and any other item marked food-contact in the item master) may be bought only from a supplier holding a valid food-grade certificate on file in Bahi. The certificate must be uploaded and checked before the first order is placed. An expired certificate counts as no certificate.
The clause scenario 1 needs. 61 words. The scenario passes only if the reply says no, cites “6.2”, and writes nothing to Bahi.

Cutting the documents

We will fetch pieces, not whole documents. How we cut decides what can be found.

The naive cut: a window of N words. Slide it. Watch §6.2 land mid-window, sharing space with §5 and §6.1, with no id you could cite.

The good cut: one clause per chunk, whole, with its heading path attached. Its id is its citation.

ChunkA piece of a document small enough to be one idea, with enough context to stand alone.

One chunk, zoomed in

Every chunk carries five things besides its words.

  • 1An id that is the citation: POL-PUR-001 §6.2.
  • 2A heading path, indexed with the text, so “6.2” is never an orphan.
  • 3A version and effective date, for freshness.
  • 4An audience, for permissions.
  • 5A status: in force, replaced, or not yet in force.
Fig. 4. The chunker split the corpus into 252 chunks; Kavita's index holds 247 of them (logs/retrieval_eval.json).

Keyword search: BM25

Score each chunk by the question's words it contains. Rare words count more (idf); repeats help less and less; long chunks are discounted.

score(q,d) = Σt∈q idf(t) · tf·(k₁+1) / (tf + k₁·(1−b+b·|d|/avgdl)) idf(t) = ln(1 + (N − nt + ½)/(nt + ½)) k₁ = 1.2, b = 0.75, N = 247 chunks

Embeddings: meaning as a direction

An embedding model turns a text into a list of numbers. Ours, bge-small-en-v1.5, gives 384.

Texts that mean similar things point in similar directions. We compare directions with the cosine: 1 is the same direction.

Every dot is one real chunk, its 384 numbers squeezed to two. The star is a question. Hover a dot; switch questions.

For Kavita's question, §6.2 has the highest cosine of all 247 chunks: .

It runs on a laptop CPU, needs no key, and gives the same numbers every run. We cache them, rounded, so a notebook replays exactly.

Where each method goes blind

Rank of the right clause, among 247, for two questions. Lower is better; “–” means not in the top 10.

Keywords miss meaning“better price” matched “grade 304 or better”. BM25 cannot tell senses apart.
Embeddings miss codesERR-PO-0412 is a string of letters and digits, not a meaning. The model has nothing to point at.

Hybrid, then rerank

Reciprocal rank fusion: each list gives an item 1/(60 + rank). Ranks, not raw scores, so BM25's 21 and a cosine of 0.76 can be added.

A reranker (a cross-encoder) reads the question and one candidate together and scores the pair. Too slow for 247 chunks; fine for the top 20.

Press the four buttons. Same question, real scores.

Our pipelineBM25 top 20 + embeddings top 20 → RRF → top 20 → rerank (ms-marco MiniLM, CPU) → top 4.

Ranking, measured

33 of our 40 test questions have a gold clause. For each method: how often is it first (recall@1), and how often in the top 5?

No model calls here: ranking only. It is cheap to measure, so measure it every time you change the chunker or the model.

Hybrid + rerank put a gold clause first on 28 of 33 and in the top 5 on all 33. Neither BM25 nor embeddings alone got all 33 into the top 5.

Citations you can check

Because a chunk's id is its citation, a citation is a key we can look up, not decoration.

Two checks, in code:

  1. 1Does it exist? Is POL-PUR-001 §6.9 a real clause? (It is not.)
  2. 2Was it in front of the model? A real clause the model never received is a guess that happens to be right.
Across 160 graded answers from RAG, the Wiki, the full corpus and the bare model, the checker found 0 invented and 0 ungrounded citations. The model alone produced no citations at all.
CITE = r"((?:POL|MAN|AMD|HR)-[A-Z0-9-]+)\s*§\s*(\d+(?:\.\d+)?)" def check_citations(answer, context_ids, corpus_ids): cites = extract_citations(answer) return {"invented": [c for c in cites if c not in corpus_ids], "ungrounded": [c for c in cites if c in corpus_ids and c not in context_ids]} # the RAG answer to scenario 1, from our run check_citations(rag_answer, ["POL-PUR-001 §6.2"], ALL) # {'cites': ['POL-PUR-001 §6.2'], 'invented': [], 'ungrounded': []}

Who may read what

Kavita is PUR-EXEC. HR-CONF-007, the salary bands, is “hr only”.

Filter before ranking: build each user's index from only what their role may read. What is not in her index cannot reach her context window, whatever the prompt says.

Filtering the answer afterwards is too late: the text is already in the model's context.

Rules change

An amendment names the clause it replaces and the date it takes effect. The retriever reads that date against Bahi's clock.

In force: the old clause leaves the index; the amendment answers. Not yet in force: both stay, each labelled with its dates.

Drag the date. Watch which certificate rule and which direct-order limit apply.

Documents explain rules. The ERP holds facts.

“How many gaskets do we have?” has an answer: 54,000 in Pune. It is in Bahi's stock table, it changes every hour, and no document holds it.

The worst outcome is a confident number from an old document. Our approval matrix has a worked example at ₹11.90 a gasket; ask “what did we last pay?” and that example is a trap.

So the tool answers rules, and sends facts to the ERP tools: stock_position, check_cost_centre, order_status, last_purchase.

The LLM Wiki: compile once

Andrej Karpathy's idea: instead of searching raw documents on every question, have a model compile them once into linked pages with an index, the way a compiler turns source into a program.

Plan the pages (one call). Write each page from its sources, citing every rule (one call each). Build the index and lint it in code: every citation must exist, every link must resolve.

At question time: read the index, pick up to three pages, answer from them.

One tool

Everything so far, behind one tool the agent can call. Its description says what it does not know.

It returns clauses with citations and their status, or a plain answer_in_documents: false.

It is bound to a user and a date when it is built, so the model cannot ask for someone else's documents.

RAG against the Wiki, 40 questions

20 policy, 8 manual, 5 freshness, 2 permission (Kavita asks for HR's page), 5 traps (live facts). One model, gemini-3.8-flash, the same answer instructions. Graded by code only: facts by regex, citations by clause id. No model judge.
