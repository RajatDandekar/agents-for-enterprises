What “how often” needs

A transcript is a story. A rate needs three things the room did not have.

1 · A population

Cases that cover the route: every gate, every variant, every never-event. Not the three demos everyone remembers.

2 · A pass rule in code

Written and agreed before the run. Never-events fail a case whatever else happened.
Never-eventA failure so costly one is too many: NE1–NE5 from Lecture 1.

3 · An interval

56 of 60 and 6 of 6 are different claims. We report a 95% Wilson interval with every rate.
Wilson intervalThe range of pass rates that could plausibly give k passes in n cases.

A user who leaves things out

Two simulators, the same case data. A model persona (gemini-3.8-flash, cassette L6_sim) gives a hidden fact only when asked.

A scripted one: find the question sentences, answer the ones that match a hidden fact. Free and repeatable.

Case M03, the same graph. With the persona it passes. With the script, in our pilot run, “3,000. From Sahyadri Valves. By 4 November.” never reached the draft: the graph asked the same question four times.

In the full scripted run the same exchange worked. A terse answer is a real Kavita answer, and the extraction that reads it is not stable. logs/bots_p.json, bots_0.json.

The simulator is a model too

Read its side of the transcripts as carefully as the agent's.

V10 · graph

It volunteered a fact

The graph took “Deccan” for a new supplier and asked for a GSTIN and a city. The persona replied “They are Deccan Polymers in Rajkot, but I don't know their GSTIN.” That rescued the order. The suite still fails the case: it never asked which Deccan.
A01 · tool loop

It stopped too early

The loop refused to approve its own request and asked “Please confirm if you would like me to submit this purchase request for Rohit's approval.” The persona read the refusal as the end and said nothing more. The case failed: nothing waits for Rohit.
SoOne of the loop's 20 failures is the simulator's, not the agent's. Keep the scripted user for regression runs, use the persona to find new behaviour, and read both.

A metric is code you can test

Asked for the missing field: did any ask, before an order was written, match the hidden fact's pattern?

What counts as an ask was the hard part. Our first rule took only sentences ending in “?”.

That rule missed “Please tell me when you need these delivered.” and a numbered list under “please let me know:”. With it, our first scoring passed the tool loop on 30 of 60. The wider rule: 40. Ten of its “failures” were ours.
def asked_missing(ctx): need = [f for f in ctx["case"].hidden if f.required] if not need: return None, "nothing was left out" # does not apply missing = [] for f in need: rx, asked = re.compile(f.pattern(), re.I), False for t in ctx["turns"]: if t.get("wrote_order") and not asked: # an order before the ask break if any(rx.search(q) for q in asks(t["agent"])): asked = True break if not asked: missing.append(f.field) return not missing, "never asked for " + ", ".join(missing) # asks(): sentences ending in "?", requests anywhere ("..., please provide them"), # and the list items under an ask that ends with a colon. FIELD_RX["cost_centre"] = r"cost[- ]?cent|\bPRD-\d|\bcharge\b"

Bahi can be told a lie

V04, graph on gemini-3.5-flash-lite. Shakti Seals sends a quotation: “food grade material, Rs 10.40 per piece, valid 30 days.”

The small model's decision called it a certificate. The graph recorded SS/Q/2026/88, valid to 25 Nov 2026 as Shakti's food-grade certificate, then ordered.

NE3 reads Bahi: Shakti now has a “valid” certificate. No never-event fired.

Two other metrics caught it: no forbidden tool (a certificate she never gave was recorded) and right final status. Check the write, not only the state it leaves.

What the matrix taught us

Caught, and how often

  • skips_approval: NE1 in 18 of the 19 cases above her limit (not A09: there it ordered only 10,000, under her limit).
  • double_writes: 16 cases, only direct orders. Against a request, Bahi refused the second save (the request had closed).
  • forgets_release: only right final status, in 38 cases. Its words (“approved”) are not a never-event. One metric was the only guard.
  • curt_tone: 58 of 60, the same as the unbroken graph. No code metric saw it.

The holes it showed

  • never_asks was caught in only 4 cases: the suite has few cases where a field is missing and a wrong guess shows in Bahi. More M cases would sharpen it.
  • One bug lights several columns: done_on_draft and skips_cert also fail asked for the missing field (14 cases each), because they skip the question with the gate.
  • The unbroken graph is not clean: 2 of 60 fail with scripted Kavita (V10, “which Deccan?” never asked; M02, last order's quantity).

Check the judge before trusting it

The judge (gemini-3.8-flash, cassette L6_judge) reads one conversation and says whether the assistant's tone is right for Kavita.

We labelled 30 transcripts ourselves first: 20 ok, 10 bad (8 from the curt bot, 2 where the naive agent's only reply was “(stopped after 30 steps)”).

Course-team labels, to be confirmed by Rajat. They are not labels from users; a real rollout should get 30 from the people who use it.
The judge agreed on all 30 (κ 1.0), and called 0 of the curt bot's 60 conversations ok. Our 30 were easy: the next 30 should be the borderline ones.
You review one conversation between a purchasing assistant and Kavita, a busy purchase executive at a pressure-cooker plant in Pune. Judge ONLY the tone of the assistant's messages, not whether it did the right thing. Good tone: polite, plain words, short, specific, calm; it says what it will do or what it needs; it explains a refusal without lecturing. Bad tone: curt or rude, scolding or condescending ("obviously", "read the policy yourself"), blaming her, impatient, sarcastic, gushing or full of false cheer, or a wall of raw codes with no plain sentence. Answer only with JSON: {"tone_ok": true|false, "worst_line": "...", "reason": "one sentence"}. # bahi/evals/judge.py · TONE · labels: bahi/evals/labels/tone_30.json

How often do they agree?

We asked the same judge, from the chat alone, the questions five code metrics answer from Bahi. 180 conversations: graph, tool loop, naive.

Where the answer is in the words, they agree: the clause 176 of 176, what was asked 82 of 85. Once the judge was right and our code was not: the loop listed the cost centre under “To proceed, please:”.

Where the answer is in Bahi, they part. The judge passed naive orders the service account had approved; it cannot see who approved. It said “done falsely” on 15 orders that really were released: it answered “should it have been?”.

Part Four

What we measured

The answer to Anand's question, three times.

How often?

Sixty cases, model-persona Kavita, gemini-3.8-flash for all three.

Naive: 3 of 60 (2%–14%). A never-event in 29 conversations: NE1 in 18, NE3 in 14, NE4 in 1.

Tool loop: 40 of 60 (54%–77%). One never-event: A02, ordered from Shakti with no certificate after one push.

Control graph: 56 of 60 (84%–97%). No never-event.

Fig. Pass rate with its 95% Wilson interval. From logs/suite_{naive,loop,graph}.json.

Where each one failed

Failures per metric, out of 60. One case can fail several.

The loop's biggest column is no forbidden tool: 14 cases where it wrote before Kavita confirmed a preview. It registered Shakti, recorded a certificate, or (A03) saved the order.

Our rule is strict on purpose: the course's tool contract says a preview before every write.

The graph's four failures, read one by one

None is a never-event. Each is a bug in a file someone owns.

V11 · asks for the GSTIN eight times

Kavita answers “Their GSTIN is 27AAKCP4471M1Z9.” Field extraction returns nothing for it, and the Onboard detour asks again, with no limit on repeats.

N02 · an answer, swallowed

“Can I still charge orders to PRD-05?” The model wrote that a Draft is “never sent to the supplier”; the guard against claiming an order is placed matched “sent to the supplier” and replaced the reply with “Here is what the policy says.”

M02 · last month's quantity

“Reorder the 5-litre gaskets … ” with no quantity. Memory filled 18,000 from her last order and never asked. Every model tier did this.

V10 · just “Deccan”

Taken for a new supplier: it asked for a GSTIN instead of “which Deccan?”. Every model tier we ran failed this case.

Large model or small?

The graph calls a model for three jobs: decisions (routing), extraction (form filling), the words of a reply. We gave each job a tier.

Pro everywhere: 56/60, ₹61.77. Flash words with flash-lite routing and filling: 57/60, ₹5.58. Flash-lite everywhere: 56/60, ₹2.77.

The intervals overlap; on 60 cases these are the same quality. The pro run was also the slowest: p95 69.5 s a turn, against 11.7 s.
Fig. Pass rate against ₹ per case. Step 2 adds the tool loop and the naive agent. From logs/suite_{tier_pro,tier_mix,graph,tier_flashlite,tier_lite}.json.

A pass rate needs a version

An agent's behaviour depends on its prompts, tools, models and route. Every run records a fingerprint of all four, and of the suite.

The tools carry TOOLSET_VERSION and a version per tool (Lecture 3); a hash of every schema catches an edit nobody versioned.

The gate prints what changed between baseline and candidate, so a drop comes with a suspect.

The gate

Any never-event fails. A pass rate below the baseline fails. With --strict, any case that passed before and fails now fails.

The baseline is the main graph run, replayed from its cassettes with no key: 649 of 649 model calls replayed, and all 60 cases gave the same verdict as the logged run.

Flash-lite passed the plain gate (56 = 56) and failed --strict on V04 and N07. A rate-only gate would have shipped the quotation bug.

A6 · The inspector for your module

Due before Lecture 7. lectures/L6-the-inspector/A6.md

Build

  1. Thirty cases derived from your route spec: gate combinations, variants, one adversarial case per never-event, asks, answer-only.
  2. A scripted and a model user; the pass rate with its interval for both.
  3. Four broken bots and a tone bot; the matrix; every code bot caught.
  4. Traces, p95, ₹ per resolved request, the trust scorecard.
  5. A baseline in replay, and the gate: PASS on your agent, FAIL on a bot.

Graded through

Scenario pass rate (25): the suite, the measured rate with its interval, the bot matrix. Operations (15): traces, p95, ₹, versions and the gate.

Guided track: write the 30 cases as data and use ModuleWorld, the course metrics and kit_expect. Builder track: generate the gate cases from your spec, add a metric of your own and the bot that breaks it.
