Check yourself

1. Kavita asks "how many days will the gaskets last?" Which pieces answer it?

L4's check_stock gets the numbers from Bahi; L2's model writes the sentence; L7's identity makes sure it is Kavita's view of Bahi.

2. Why did Rohit need his own conversation?

Approval is his authority. His chat runs in his session; Kavita's chat could never approve, by design.

3. Neha recorded 12,000 then 8,000. What made the second one close the order?

Bahi did: the receipt tool reports what Bahi holds, CLOSED once all 20,000 arrived.

4. Which piece would you remove first, and what would break?

Any of them breaks something you measured: no memory, no §6.2; no trust, NE1 with SVC_AGENT; no loop, no order after the approval.

The six promises, in apply_leave

Typed inputs. Errors with a next step. A preview that saves nothing. A key from the content, looked up before the write and after a timeout. A receipt read back from Bahi. Only the session it is given.

The receipt names HD in plain words, so the model cannot call a held leave approved.

def run(s, leave_type, from_date, to_date, reason, confirm=False): emp = _bahi(s, "lv_emp_get", user_id=s.user_id) # only her own session days = _days(s, from_date, to_date) key = content_key("LV", s.user_id, emp["emp_cd"], leave_type, from_date, to_date) found = _bahi(s, "lv_list", client_ref=key)["rows"] # look up before writing if found: return {**_receipt(s, found[0]["lv_no"]), "already_done": True} bal = {r["lv_cd"]: r["bal"] for r in _bahi(s, "lv_bal_get", emp_cd=emp["emp_cd"])["rows"]} unpaid = max(0, days - bal.get(leave_type, 0)) preview = {..., "days": days, "unpaid_days": unpaid, "approver": f["lv_appr"]} if not confirm: # preview saves nothing return {"ok": True, "preview": preview, "warnings": warnings} try: lv_no = _bahi(s, "lv_save", ..., client_ref=key)["lv_no"] except ServiceTimeout: # a lost reply lv_no = _bahi(s, "lv_list", client_ref=key)["rows"][0]["lv_no"] return _receipt(s, lv_no) # read back, HD in words

Check yourself

1. Scenario 2 broke §5.2 every run. Fix the prompt, or the tools?

Both, and a guard. Knowledge finds §5.2; apply_leave needs a forward-to; the guard refuses Diwali-run leave for stores staff that is not forwarded.

2. Why name the tool apply_leave and not lv_save?

The model chooses tools by what people ask for. "Apply for leave" is the activity; lv_save is one of three services behind it.

3. Your kit's write tool times out after Bahi saved. What must happen on the retry?

The key finds the saved document and the tool finishes from there: one document, the right receipt.

4. Which of the six moves can you skip for a read-only module?

None entirely: even reads need identity (who may see what), knowledge, and tests. Only the write promises shrink.

Two rulesEvery number you say comes from your own logs. If the live run hangs, say so and show the replay: an honest recovery scores better than a smooth demo.

The client changes a rule overnight

The demo-day changeA new rule or a new path for your module, announced at 9 AM on Saturday in the client's words. You absorb it by 7 AM on Sunday.

A policy lives only in a document; Bahi does not check it. A variant is a path through the screens Bahi supports and your module never took.

On demo day the grader runs a hidden test of the change on your agent, in replay: 10 points.

Why a change at all

A demo that works once proves little. Real plants change a rule every month. What the client is buying is not the demo; it is how fast your build absorbs the next change without breaking the rest.

Your gate from Lecture 7 is how you prove "without breaking the rest".

Is each change fair?

Before announcing, each change is run against its kit with scripted agents: Friday's careful run must fail the hidden test, the careful run after the change must pass, the careless run must be caught.

Fair: of kits, re-run on Modal today, with each kit's own four scenarios still passing and all eight kits installed together. (logs/demo_changes.json)

What we can say, and what we cannot

Measured

  • Kavita's order end to end, every step logged and read back.
  • No service account in Bahi's log; guards refusing real attempts.
  • No duplicate order after 50 injected faults, with keys.
  • Eight kits that install together and test clean; eight fair changes.

Not yet

  • Pass rates are on six cases and three runs: a start, not a guarantee.
  • Empty model replies still end some runs early.
  • Latency under a full class, and the provider's own limits, are not yet measured.
  • A real plant's data, security review and audit: outside this course.
