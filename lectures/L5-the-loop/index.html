Who drives the next step?

Two extremes, on the same order.

Extreme 1 · the person drives

One round per message

A loop

The model asks for a tool, reads the result, and asks for the next one, again and again, until the job is done or it needs Emma. This is what Lecture 4’s orders really ran on.
AgentA model in a loop that chooses its next step from what it has seen so far, until the job is done or it needs a person.

Section 2 of 7 · The loop
Last sectionAn agent is a model in a loop. Now we open the loop, one step at a time.

What happens inside one turn of the loop?

The smallest loop

Fifteen lines. No limits, no rules, no memory beyond the list of messages.

1 · Think. The model reads everything so far.

2 · Done? If it answered in words, stop.

3 · Act. Run each tool it asked for.

4 · Observe. Put each result back in, and go round again.

Read line 7 again: while True. Nothing here ever stops a loop that keeps asking for tools. That is the harness’s job, Section 3.

ReAct: reason, then act

The idea behind the loop, from a 2022 paper (Yao et al., “ReAct”).

Thought

Reason in words

“I need the stock of BAT-500 first.”
Action

Pick one tool

The name of a tool and its arguments: check_stock {"item_code": "BAT-500"}
Observation

Read the result

Our code runs the tool and writes the result back. Then the next Thought.
ReActA way to run a model as an agent: it writes a thought, then an action; our code runs the action and returns an observation; repeat until a final answer.

ReAct as plain text

Before tool-calling APIs, the loop was a prompt. The tools are listed as lines of text.

The model must write in a fixed format: Thought, Action, Action Input.

Then it must stop. Our code writes the Observation.

The text loop, on a stock question

The parser is the whole trick

The model only wrote text. Our code finds the Action line and the JSON after it.

Where text breaksA missing Action Input line, broken JSON, or the model writing its own made-up Observation. In our runs on this model: , and format errors, and invented observations even without the stop sequence. Older models broke often; the parser must still check.

When does the loop end?

In the smallest loop, only one way. In ours, five.

The model ends it

It answers in words

No tool calls in the reply: the message is done. This is the only stop in the smallest loop.
The harness ends it

Our code says stop

  • the step limit is reached
  • the token budget is used up
  • three failures in a row
  • a request now waits for an approver
Why it mattersA model that never stops calling tools would spend money for ever. A loop that stops too early leaves the job half done. Section 3 measures both.

Section 3 of 7 · The harness
Last sectionThe loop: think, call, observe, repeat. On its own it never stops.

What keeps a loop safe?

The harness

HarnessThe code around the model that runs the loop: what goes in, what may run, when to stop, and what is remembered.

The model picks the next step. The harness decides what it can pick from, and for how long.

Part 6 · Error recovery

When a tool fails, the harness can help the model, or get in its way.

2 · Never repeat a refusal

The same call that failed

3 · A loop guard

The same call a third time

is refused; three failures in a row stop the loop.
Measured on the six jobsRecovery on or off made no difference: right with it off. On these jobs no call failed twice. So we broke Ledgerline on purpose.

Find and fix · the lost reply

Ledgerline saves Emma’s request, then the reply never comes back. Rule 2 thought it was a refusal.

With the first version, the retry was refused. The model told Emma it “may or may not have saved”, and stopped. The request sat in Ledgerline with no order.
A lost reply is safe to retry only because the tool looks itself up before it saves (Lecture 4’s idempotency). The fix: remember refusals, not timeouts.
An honest failure of our own harness, found by measuring. A rule that sounds safe can still be wrong: test it on the failures you expect.

Part 7 · The approval is a pause

£285,600 is above Emma’s limit. Ledgerline sends the request to Daniel. What should the loop do now?

Without a pause

Keep going

Try to create the order (Ledgerline refuses: “not approved”), check the status again and again, or wait inside the loop for hours.
With a pause

Stop, hold the writes

The harness sees “WAITING FOR APPROVAL”, notes who it waits for, refuses every write until then, and lets the model tell Emma.
PauseThe loop stops and saves where it is, because a person must act first. It carries on only when the system of record says that person has acted.

The pause, tested: “Daniel approved it”

Next morning Emma writes that Daniel approved it. He has not. Recorded, 2 runs each.

Read it honestlyThis model checked Ledgerline by itself and told the truth. The pause makes that a rule, not a habit: Ledgerline is read first, every time, and the model is not even called.

The model and the harness: who owns what

The same model behaved differently in every harness we tried. That is the point.

The model
  • which tool next, with which arguments
  • several calls at once, or one
  • what to tell Emma
  • when it thinks the job is done
The harness (our code)
  • the prompt, the history, the tool list
  • how many steps, how many tokens
  • which failures to retry, which to refuse
  • pausing for a person, and reading the truth from Ledgerline
  • saving the state for tomorrow

When to use which

From the extremes to a rule of thumb.

Write it down: a workflow
  • you can list the steps, and they rarely change
  • the same input must give the same result
  • it runs often, so cost and speed matter
  • an auditor must see exactly what will happen
Let it choose: an agent
  • the next step depends on what you find
  • requests come in many shapes, like questions
  • it runs rarely, or a person is in the loop
  • a stop is worse than a careful try
The ruleWhen you know the order, write it down. When you do not, let the model choose, inside a harness. Most real systems do both.

What we learnt today

Five lines to keep.

  1. 1An agent is a model in a loop that picks its next step from what it has seen.
  2. 2The loop is four lines: think, check for words, act, observe. It never stops by itself.
  3. 3The harness is ours: prompt, history, tools, stops, budget, recovery, the pause, tomorrow.
  4. 4A workflow is the steps written down: cheap, the same every time, and it stops when the job is not its own.
  5. 5When you know the order, write it down. When you do not, let the model choose, inside a harness.
