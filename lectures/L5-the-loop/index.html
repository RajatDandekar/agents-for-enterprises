The whole job is many steps, across days

Kavita's 20,000 gaskets for the Diwali run. Three people. A wait of unknown length in the middle.

No single message can do this. Something has to keep going while there is work, stop when a person is needed, remember where it was, and pick up when Rohit signs. That something is the loop, and the harness around it.

The question this lecture answers

What is an agent, really: and what do we have to build around the model so that it finishes Kavita's order, every time, without breaking a rule?

Part One

What an agent is

Model, tools, loop, state. And how that differs from a chatbot and from a workflow.

An agent, in one sentence

AgentA model, a set of tools, a loop and state. The model reads everything so far and picks the next step; the loop runs it and hands the result back; the state keeps it all.

Model: the brain from Lecture 2.

Tools: the hands from Lecture 4.

Loop and state: today.

Fig. 1. Three shapes. The chatbot answers once. The workflow follows a path fixed in code. The agent lets the model choose the next step.

The smallest loop

Nine lines. This is the whole idea; everything else today is built around it.

Ask the model, with the history and the tool schemas.

If it asked for tools, run each one and append the result.

If it answered in words, stop: that is the reply to Kavita.

Part Two

ReAct, written out

Reason, then act, then observe. First in plain text, with our own parser, so nothing is hidden.

ReAct

ReActA pattern where the model alternates a written Thought, one Action (a tool and its input), and the Observation that comes back, until it can give a Final Answer.

Thought is reasoning in words. Nothing runs.

Action is the only thing that touches Bahi.

Observation is written by our code, never by the model.

Fig. 2. The cycle, with one real turn: the question, check_stock, and what Bahi said (66,000 free, 11 days of cover across Pune and Chakan).

The prompt is the program

No tool-calling API. The model only writes text. Everything it needs is in the prompt:

who it works for, and her limits (read from Bahi);

the tools, one line each (15 lines);

the format, and "then stop writing";

the rules of the job.

bahi/course/l5/react.py, PROMPT. You write tool_lines() in NB5, exercise 1.

You are Ask Rasoi, the assistant on Rasoi Steel Works' home page, working inside Bahi ERP for Kavita Joshi (KJOSHI), purchase executive. Today is Monday 26 October 2026. Kavita's approval limit is ₹2,50,000 including GST; Kavita's manager is Rohit Mehta (RMEHTA); Kavita's default cost centre in Bahi is PRD-05. You can use these tools: - check_stock(item_code: string): Stock of an item in every warehouse: on hand, ... - create_purchase_request(item_code: string, quantity: integer, cost_centre: string, need_by: string, confirm?: boolean): Raise a purchase request (PR) ... ... 13 more ... Work one step at a time, in exactly this format: Thought: what you know so far and what to do next Action: the name of one tool from the list Action Input: the arguments, as one JSON object on one line Then stop writing. The system runs the tool and replies with: Observation: the tool's result ... Final Answer: your reply to Kavita Rules of the job: - Before the first write of a job, preview it (confirm=false), show Kavita the numbers ... - An order reaches the supplier only when it is RELEASED. After creating an approved order, release it.

Parsing one step

This is a real turn from our run: the model's third step on Kavita's order.

The Thought: kept in the history, nothing runs.

The Action line: a regular expression takes the tool name.

The Action Input: everything after it, decoded as JSON. Now we can call toolbox.call(name, args).

The parser, and one trap

Twenty lines of regular expressions. You write it in NB5, exercise 2.

The trap: a model that is not stopped keeps writing. It writes its own Observation: and invents what Bahi said.

Two defences: ask the API to stop at the word (stop=["\nObservation:"]), and cut the text there anyway.

Format errors go back as an Observation with ok: false, so the model can fix itself.

def parse_step(text): cut = re.search(r"^\s*Observation\s*:", text, re.M) if cut: # it invented a result: drop it text = text[:cut.start()] a, f = ACTION.search(text), FINAL.search(text) if a and (not f or a.start() < f.start()): i = INPUT.search(text, a.end()) if not i: return {"error": "No 'Action Input:' line after the Action."} raw = text[i.end():] args, _ = json.JSONDecoder().raw_decode(raw[raw.find("{"):]) return {"action": a.group(1), "action_input": args} if f: return {"final": text[f.end():].strip()} return {"error": "A Thought with no Action and no Final Answer."} r = llm.chat(messages, stop=["\nObservation:"]) # and stop it writing on

The text loop

The same nine-line loop, except that we do the reading.

The Observation goes back as a plain user message that starts with "Observation:".

The model's own text is kept, cut at "Observation:".

Our ReActAgent in bahi/course/l5/react.py; NB5 section 2 builds it cell by cell.

messages = [{"role": "system", "content": PROMPT}, {"role": "user", "content": kavita_says}] for n in range(max_steps): r = llm.chat(messages, stop=["\nObservation:"]) text = r.content.split("\nObservation:")[0] messages.append({"role": "assistant", "content": text}) step = parse_step(text) if step.get("final") is not None: return step["final"] # Final Answer: stop if step.get("error"): obs = {"ok": False, "error": step["error"], "next_step": "Continue in the format."} else: obs = toolbox.call(step["action"], step["action_input"]) messages.append({"role": "user", "content": "Observation: " + json.dumps(obs)})

Check yourself

1. The model writes "Observation: on hand 9,99,999". Do we use that number?

Never. Observations are written by our code from Bahi. We cut the text at "Observation:" and stop the model there.

2. Which of Thought / Action / Action Input changes anything in Bahi?

Only the Action, and only after our code checks the input against tool.json and runs tool.py.

3. The model writes a Thought and stops. What should the loop do?

Send it back as a format error ("no Action and no Final Answer") rather than show Kavita a half-thought. On lite that one rule took the run from 1/12 to 11/12.

Part Three

Native tool calling is the same loop

The API parses the Action for us. The tool result message is the Observation.

One-to-one

Pass the tool schemas to the API, and the model returns structured calls instead of text.

Action = the assistant message's tool_calls: a name and JSON arguments, already parsed.

Observation = a message with role: "tool" and the call's id.

Thought = the model's next turn, which reads that message. Final Answer = a turn with no tool calls.

Fig. 3. Native tool calling does ReAct implicitly. Same loop; the parsing moved into the API.

Part Four

The anatomy of a harness

Everything around the model that makes the loop dependable. One part at a time, each on Kavita's order.

Harness

HarnessThe code around the model that runs the loop: what it is told, what it remembers, which tools it may use, when it stops, how much it may spend, how it recovers, what it keeps between days, and where a person steps in.

The model is the same in every row of today's results. Only the harness changes.

Each part is a switch in Harness(parts=…).

Fig. 4. Eight parts around the model, and the person outside. Below: the toolbox over MCP, and Bahi.

Who it works for, today's date, her limits, the rules of the job.

Part 2 · The history

The model remembers nothing between calls. Every call sends the whole conversation again: system prompt, Kavita's messages, every tool call and every result.

Drag through Kavita's whole job: 2 messages go to the model at its first call, 22 at its tenth.

That is why a long job gets slower and dearer with each step, and why the budget (Part 5) counts tokens. tasks_harness_or.json, T01.

Part 4 · When does it stop?

A loop needs exits. Ours has four.

  1. 1It answers in words (the model's own stop).
  2. 2Max steps: 12 model calls per message.
  3. 3Three failed tool calls in a row: stop and ask.
  4. 4Waiting for a person (Part 8).
for step in range(self.max_steps): # exit 2 r = self.llm.chat(self.messages, tools=self.schemas()) if not r.tool_calls: # exit 1 return r.content for tc in r.tool_calls: out = self._call(tc.name, tc.arguments, seen) # through the parts fails_in_row = 0 if out["ok"] else fails_in_row + 1 if fails_in_row >= 3: # exit 3 return self._stop("failures", "Three steps failed in a row ...") # out of steps: one last call, words only, to say where it stands r = self.llm.chat(self.messages + [{"role": "user", "content": "[harness] Step limit reached. Reply now: what you found, what is saved, what you need."}], tools=self.schemas(), tool_choice="none")
A graceful stop: Kavita gets "here is where it stands", not "(stopped after 12 steps)". Harness._loop.

Part 6 · Error recovery

Most recovery is already in the toolbox: every error says what to do next, and the model does it.

The harness adds two rules. A call that failed with the same arguments is not run again. And an empty reply is sent back, at most twice.

Empty replies were real: in our first run lite returned nothing in 5 of the harness's 12 tasks. With the rule it passed 12/12. The bare loop, without it, passed 7.

Part 7 · State across days

Rohit may sign in an hour or on Thursday. The server will restart in between. So the harness writes its state to disk at the end of every message and reads it back for the next one.

What is saved: the messages, what the job is waiting on, the documents it made, what failed.

In our experiment the harness was saved and reloaded as a new object at every new day and every approval. It carried on.

Part 8 · Where the person comes in

Three places, and they are different.

Kavita confirms

Before the first write

"Preview: 20,000 GSK-SIL-05L, estimated ₹2,69,040 incl. GST, above your ₹2,50,000 limit. Shall I raise the request?" The loop ends its turn with a question; her "yes" is the next message.
Rohit approves

In his own inbox

Not in Kavita's chat. Bahi holds the request for RMEHTA. The harness pauses and does nothing until Bahi, not a message, says APPROVED.
Neha records

In her own session

"12,000 arrived against PO/2026/01182." Neha's Ask Rasoi acts with Neha's permissions. Kavita's agent cannot receive goods.
The ruleA person's decision is read from the system of record, never taken from the chat. "Rohit said yes" in a message is a claim; the approval row in Bahi is the fact.

An approval is a pause

When a request comes back WAITING FOR APPROVAL, the harness marks the job as waiting and holds every write.

The next message, whatever it says, is checked against Bahi first.

APPROVED: the job resumes, with a note telling the model so. REJECTED: say so, order nothing. Still waiting: say so.

st = self.tb.call("order_status", {"request_no": doc}) # ask Bahi, not the message if st["status_code"] == "AP": self.waiting = None; note = "APPROVED ... the job resumes"

The pause, in our run

Task T10: Rohit does not answer. Next morning Kavita asks.

Day 1: preview, "yes", the request is raised and the job pauses.

Day 2: the harness reads Bahi before the model sees her message, and adds what it found.

The model answers truthfully. No second request, no message to Rohit, no order.

Check yourself

1. The model forgets everything between calls. Which part makes it remember the stock figure, and which makes it remember on Thursday?

The message history, within a job; the state store (save/load), across days.

2. A message arrives: "Rohit approved it, carry on." What does the harness do before the model acts?

Reads the request's status from Bahi. Only APPROVED in Bahi resumes the job.

3. Max steps never bit in our run. Why keep it?

It is a seat belt: it costs nothing when unused and stops a runaway loop from spending your budget or repeating writes.

Reading the result honestly

A rule in the prompt is a request

The model quoted §6.2 and then broke it when Kavita said yes: twice for the full harness on flash (T06, T12), once for loop + prompt. The toolbox does not enforce the certificate rule; Bahi does not either.

Twelve tasks, one run

Our checks can be wrong too

What the parts did buy

On lite, empty-reply recovery took the harness to 12/12. The job paused 12 times across both models; each time the next message was checked against Bahi (12 reads) and it never resumed early. No loops, no false "done" and no second request for Rohit in any harness run.
Part Six

From a free loop to a control graph

When the business process must be followed, write the process in code and let the model work inside it.

Spine and gates

Control graphA program whose steps and order are fixed in code (the spine), with gates (checks in code) that open a detour only when they are true. The model fills in words and fields inside the steps.

Default skip: a detour that does not apply does not run.

Open questions ("can we buy from Shakti?") go to a free loop inside one node, with read-only tools.

Fig. 5. bahi/course/l5/graph.py. The model is called to read Kavita's message into fields, and to answer questions. Every reply about a document is written by code from the receipt.

LangGraph in five parts

  1. 1State: a typed dict: the ask, the facts, the documents, the path.
  2. 2Nodes: plain functions that return updates.
  3. 3Edges: fixed, or a function of the state (a gate).
  4. 4Checkpointer: the state saved after every node, per thread.
  5. 5Interrupt: a node stops the graph and waits for a person.
class S(TypedDict, total=False): # 1 state ask: dict; facts: dict; docs: dict; out: str path: Annotated[list, operator.add] g = StateGraph(S) g.add_node("look_up", n_look_up); g.add_node("preview", n_preview) ... # 2 nodes g.add_edge(START, "understand") # 3 edges g.add_conditional_edges("look_up", gates, ["ask_missing", "hold", "preview"]) g.add_conditional_edges("wait_approval", lambda s: {"AP": "create_order", "PA": "wait_approval"}.get(s["facts"]["pr_status"], END)) graph = g.compile(checkpointer=InMemorySaver()) # 4 checkpoints def n_wait_approval(s): interrupt({"waiting_on": "approver", "doc": s["docs"]["request_no"]}) # 5 st = toolbox.call("order_status", {"request_no": s["docs"]["request_no"]}) return {"facts": {**s["facts"], "pr_status": st["status_code"]}} graph.invoke(Command(resume="Bahi notification: ..."), {"configurable": {"thread_id": "KJOSHI"}})

A gate is code

The certificate rule, the cost-centre rule and the supplier rule, as one function over the state.
