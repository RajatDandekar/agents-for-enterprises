A tool has four parts

  1. 1A name the model writes in its request.
  2. 2A description, written for a model, not a Bahi consultant: what it does, what it returns.
  3. 3A typed input schema: the arguments, in the user's words.
  4. 4A function our code runs. The model never runs anything.

How to build tools from a legacy screen, in six steps

Done for real on Bahi's purchase-order screen. Each step leaves a log the notebook and this deck read.

Screens, tasks, services, procedures

A screen is what Kavita sees. A task is one button. Each task calls a service; each service runs stored procedures, where the rules live.

The registry has 38 services (26 read, 12 write) and 13 procedures. The live runs tell us which ones each button really uses. Click a screen.

Most reads run no procedure. Every rule that matters sits behind a write.

Shown once

Real ERPs define each screen in a long activity file: controls, help keys, events, preconditions, service bindings, years of patches.

You will meet these in a real engagement. Read them for the tasks, the services and the preconditions. The rest is layout.

In the sandbox each screen is a ~30-line screen.yaml that keeps exactly those three things. We never read XML again.

The XML is fictional, written for the course. Scroll it: it does not fit, which is the point.

When services are too tangled, write a façade

Bahi's order needs a request, an approval, a Fetch, a Save with the right tax code and token, and a read-back. No single service does that.

So we write our own agent API in front of Bahi: one call per job. It still lets Bahi's procedures enforce every rule.

It may add what Bahi lacks: a read Bahi does not offer (_peek, ask IT for a view) and a near-duplicate check Bahi never had.

# bahi/agent/tools.py  (abridged)
def create_purchase_order(s, supplier_code, item_code, quantity,
                          cost_centre, need_by, idempotency_key=None,
                          rate=None, confirm=False):
    key = idempotency_key or content_key(s.user_id, supplier_code,
              item_code, quantity, cost_centre, need_by)        # 1 key
    if po_search(client_ref=key): return already_done + receipt
    gross = tax_compute(...)  ;  cc = bud_check(...)          # 2 ask Bahi
    if not confirm: return {"preview": ..., "warnings": ...}
    if gross > 50000:                                       # 3 variant
        pr = find_request(key) or pr_save(...) + pr_submit(...)
        if pr is waiting: return {"status": "WAITING FOR APPROVAL"}
    tok = po_fetch(...)["fetch_tok"]                         # 4 screen state
    try: po = po_save(..., fetch_tok=tok, client_ref=key)
    except ServiceTimeout:                                   # 5 lost reply
        po = po_search(client_ref=key)
    return _receipt(po)                                       # 6 read back

The same four mistakes, as Bahi reports them and as the tools report them (logs/intent_tool.json).

confirm=false: price it, check it, save nothing

The preview asks Bahi's own tax engine and budget check (validate once), so Kavita sees the gross value, the path and the approver before anything is written.

The reply was lost. Retry safely.

We make Bahi save the order and then drop the reply, the way a 504 does.

A raw client cannot tell “not saved” from “saved, reply lost”. It retries and writes a second order: never-event NE2.

Idempotency keyA key that names the order. A retry with the same key finds the first result. Derive it from the order's content (a hash), never uuid4(): a fresh random key on the retry looks like a new order.

Read it back: the status Bahi holds, not the message it printed

Validate once

Bahi enforces its rules. Tools ask, never copy.

The preview calls tax_compute and bud_check, so Bahi's sp_tax_compute and sp_budget_chk answer. Save still runs sp_tax_region_chk, sp_budget_chk and the variant rules. If finance changes a rule, the tools change with it.

The food-grade rule is not in Bahi at all (Purchase Policy §6.2). The tools report the certificate as a fact; enforcing it is Lecture 5's job.

Same tools, different host

On outcomes the tools carry nearly everything: a generic MCP host with a generic prompt passed as many tasks as our harness on the default model.

The gap is in how. On the small model, the generic host wrote 10 of 15 orders before Kavita said yes; our harness, none. The only difference is one paragraph of instructions.

And instructions are not guarantees. In scenario 1 our own harness set confirm=true itself and wrote an order nobody asked for. Lecture 4 turns the route into code.
