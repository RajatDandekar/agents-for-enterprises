# A4 · The Route for your module

**Lecture 4 · From Forms to Agents.** Due before Lecture 5. Builds on A3 (your 5–8 tools and MCP server).

The form did three jobs for your module too: it asked for the required fields (job 1), it knew which screen came next (job 2), and it held the half-filled document (job 5). In A4 you take those jobs off the form and give them to **a control graph, a router and a memory policy**.

## What to build

1. **A route spec, as data** (`route_spec.py` or `route_spec.yaml`), in the shape of `bahi/agent/route_spec.py`:
   - the **spine**: 5–8 steps every request walks, each naming the tools it may call;
   - the **gates**: every *if* in your module's process document, each a named predicate over the state, with the detour it opens, where it rejoins the spine, a one-line description and the rule it comes from. The default is to skip;
   - the **asks**: required fields, and which ones memory or a lookup may fill;
   - the **invariants**: the never-events of your module, and the step that refuses them in code.
2. **A control graph** (LangGraph `StateGraph`) built from that spec:
   - state = your module's draft document, the facts the route looked up, the messages and the path;
   - a checkpointer (one thread per conversation);
   - an **interrupt** for every question to the user, and one for every wait on another person (an approval, a sign-off);
   - the model is called only to extract fields (structured output), make typed decisions, and write replies;
   - a `respond(text) -> str` agent class, so your scenarios run unchanged.
3. **A router**: one typed decision (with `decide()`) that sends each message to its branch (do the job / answer a rules question / give a status / other), with a threshold below which the agent asks.
4. **One more typed decision** where your module needs a judgement (for example: is this attachment a medical certificate or a leave request? is this vendor the same as an existing one?), with options, typed fields and a confidence.
5. **A memory policy** (half a page in your README): what lives at each of the four levels (draft, session, user, company), what the user level learns and from where, how long each lasts, and what each step is allowed to read. Show `context_for_turn()` output for one real turn.

## What to submit

- `modules/<your-module>/agent/route_spec.*`, `graph.py`, and your decision specs.
- `A4_report.md`: the route as a diagram (spine + detours), the memory policy, and a table of your scenarios at this layer (pass/fail, never-events, tokens, ₹), with the log path for every number.
- The executed notebook (replay mode must work with no API key: record with `--mode auto`, then run `--mode replay`).

## Checklist

- [ ] Every gate has a name, a description, a detour, a rejoin point and the rule it comes from.
- [ ] Every gate's default is *skip*; a test shows each gate closed and open.
- [ ] No write can happen without a preview the user confirmed for that exact draft (compare keys; never a flag the model sets).
- [ ] Idempotency keys are a hash of the draft, never `uuid4()`.
- [ ] Every wait on a person is an interrupt, and the resumed node reads the decision back from the system of record, not from the message.
- [ ] After every write the document is read back; a stuck status (like Bahi's silent Draft) is fixed or reported, never called done.
- [ ] The last line of every reply about a document is written by code from the receipt.
- [ ] Decisions have options, fields, a confidence and a threshold; below it, the agent asks.
- [ ] Every decision has an explicit `unsure` option that routes to a question. (In our run, self-consistency gave confidence 1.0 on all 32 test inputs, ambiguous ones included: the model showed doubt by choosing an option, not by disagreeing with itself. See `lectures/L4-the-route/experiments/logs/decide_eval.json`.)
- [ ] When a gate and a missing field both apply, ask for everything in one question (our graph asked for the closed cost centre alone first; see case M3 in `forty_graph.json`).
- [ ] Memory: user-level facts are suggestions that the gates still check.
- [ ] Your scenarios include at least one per gate, one missing-field case and one change-of-mind case.

## How it is graded

A4 feeds the course rubric (/100) mainly through **route and authority (15)** and **scenario pass rate (25)**:

| what | points in the rubric line |
|---|---|
| Route spec complete and matches the graph that runs (gates enumerable, rules cited) | route and authority, 6 of 15 |
| Never-events refused in code (preview+confirm key check, read-back, status line) | route and authority, 5 of 15 |
| Interrupts for questions and waits; approvals read back from the system | route and authority, 4 of 15 |
| Scenario pass rate at this layer, measured, with logs | scenario pass rate (running total) |
| Router and one typed decision with a measured confidence | tools, part of 20 |

Lecture 5 adds roles and receipts (the rest of route and authority); Lecture 6 turns your gates into a scenario suite.

## Two tracks

**Guided track (configuration).** Copy `bahi/agent/route_spec.py` and `graph.py`. Rewrite only the data: spine steps, gates (as predicates over your facts), asks and the `EXTRACT` fields. Keep the node functions and change the tool calls inside them to your A3 tools. Use `decide()` as it is, with your own `DecisionSpec`s.

**Builder track (Python).** Write your own `StateGraph` from your spec: generate nodes and conditional edges from the gate list, so adding a gate to the spec adds the detour to the graph. Add a test that walks every combination from `gate_combinations()` on fake states and checks which detours open. Optional: plug a dedicated decision service into `ServiceBackend` and compare its confidences with self-consistency on your own labelled inputs (report only what you measure).
