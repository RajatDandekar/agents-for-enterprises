Part One

LangGraph from first principles

Five parts: state, nodes, edges, checkpoints, interrupts. Each one on Kavita's order.

State is the draft

A typed dict every node reads and returns updates to.

StateThe graph's memory of this one job. Each field has a reducer: how an update is combined. draft merges key by key; path appends.

draft: what Kavita wants. facts: what the route looked up. awaiting: what we asked her.

A node is a plain function

State in, an update out. No magic.

Most nodes call tools and compute. Only some ask the model, and only for words.

Here, the Ask-for-certificate detour: it searches the company's policy (memory level 4), asks the model to word the question, and appends the rule itself, verbatim, so the citation cannot be invented.

An edge is a gate

A conditional edge is a function of the state that names the next node.

GateA named predicate over the state that opens one detour. When it is false, the detour is skipped. Skip is the default.

The gates live in route_spec.py as data. The graph reads them; Lecture 6 enumerates them to write tests.

Gate("food_contact_no_cert", "Ask for certificate", detour="ask_certificate", after="check", rejoin="check", policy="Purchase Policy §6.2", description="The item touches food and the supplier has no valid " "food-grade certificate in Bahi, and Kavita has not given one.", pred=_no_cert) def _no_cert(s): f, d = s["facts"], s["draft"] if not f.get("food_contact"): return False if f.get("supplier_cert") == "valid": return False return not (d.get("cert_ref") and d.get("cert_valid_to", "") >= TODAY) # the four gates of a purchase order supplier_not_found → Onboard supplier (Purchase Policy §6.3) centre_closed → Fix cost centre (§4.1–4.2) food_contact_no_cert→ Ask for certificate (§6.2) over_limit → Approval (§5.1–5.4)

The checkpointer is the open window

After every node, LangGraph saves the whole state under a thread id.

Kavita can answer in a minute or tomorrow. The draft waits in the checkpoint, not in the model's context.

Interrupts

A node calls interrupt(payload): the graph stops and hands the payload out.

The next message resumes it: graph.invoke(Command(resume=text)). The node runs again and interrupt returns her answer.

Two kinds in our graph: ask_kavita (a question) and wait_approval (a person). After Rohit's message, the node reads the request's status from Bahi. The message is never trusted.

Fig. 5. Kavita's reorder is three invocations of one graph. From logs/six_graph.json, scenario 2.

One spine, gated detours

The spine runs every time: Understand, Route, Collect, Check, Preview, Commit, Confirm.

Each detour has a gate, and the default is to skip it.

Pick a recorded run. The lit nodes are the path the graph really took; ×2 means a node ran twice (each turn re-walks the spine from the saved state).

Part Two

Typed decisions

Some steps are judgements, not lookups. Give each one a type, a confidence, and a way to ask.

A decision with a type

“Is this upload a food-grade certificate or a quotation?”

Typed decisionA fixed set of options, optional typed fields, and a confidence. Below the threshold, the route asks the human instead of guessing.

Our backend asks Gemini for structured JSON k times at temperature 1.0. Confidence = the share of samples that agree (self-consistency). The graph uses k = 3; the evaluation, k = 5.

DecisionSpec("document_kind", "What has the user given us for the supplier's food-grade certificate?", options=("food_grade_certificate", "quotation", "other_document", "no_document"), fields={"doc_ref": "...", "valid_to": "YYYY-MM-DD", "issued_to": "..."}, guide="A quotation offers prices, even when it says the material is food grade.") d = decide("document_kind", text, context, k=5, threshold=0.8) d.choice, d.confidence, d.fields, d.sure
// a real decision from scenario 2 (logs/six_graph.json) {"name": "intent", "choice": "order", "confidence": 1.0, "sure": true, "votes": {"order": 3}, "k": 3, "threshold": 0.8}

Agreement is not doubt

32 labelled inputs, four decisions, five samples each: 160 calls, ₹3.39.

Every input came back at confidence 1.0: five samples, one answer. 29 of 29 labelled inputs were right. Move the threshold: nothing changes.

The three ambiguous inputs did not split the votes. The model put its doubt into an option: “Deccan” → none of these, five times. In the 40-case run that answer sent case D4 to onboarding.

Self-consistency measured nothing here. Give every decision an explicit unsure option and treat it as “ask”; that is the change A4 asks for.

Jev, and a slot for it

A dedicated decision-model service, such as Jev (TypeSafe's public decision API), takes the same shape: a decision name, options, input and context in; a choice, typed fields and a confidence out.

decide() takes any backend with one method. Ours is Gemini self-consistency. ServiceBackend wraps a function you write that calls a service.

We did not have Jev access. No Jev client ships with the course and no Jev number appears on any plate. Wire your own client into ServiceBackend and measure it on your own labelled inputs.
class ServiceBackend: """A slot for a dedicated decision service. `call` gets {"decision", "question", "options", "fields", "input", "context"} and must return {"choice", "confidence", ...fields}.""" def __init__(self, call, name="decision service"): ... def sample(self, spec, text, context, options, k): r = self.call({...}) return [{**r, "_confidence": float(r["confidence"])}] # one call agent = GraphAgent(erp, "KJOSHI", llm=llm, decide_backend=ServiceBackend(my_client)) # your client
Part Three

Memory at four levels

The draft, the session, the user, the company. The model never sees all of any level; each step takes the slice it needs.

What each level put into one turn

1 · Draft: the order so far, in the graph's state.

2 · Session: the checkpointer thread: what we asked, what she said.

3 · User: learned from her own orders in Bahi.

4 · Company: the policy clause the step searched for. Switch to scenario 2: “Yes, go ahead.” names no rule, so level 4 adds nothing.

Kavita's usual cost centre, learned from Bahi: PRD-05, from 4 of her 6 orders. Her usual gasket supplier: Deccan Polymers.

PRD-05 closed on 15 October. A memory that is right about her habits is wrong about today.

Reading the result honestly

What the graph bought

  • The order of steps in code: no write before Check, in every run, by construction.
  • A tenth of the tokens and a sixth of the ₹ on gemini-3.8-flash (1,23,451 vs 11,99,469 tokens; ₹9.15 vs ₹60.33 for 40 cases).
  • Fewer tool calls (212 vs 345) and a recorded path for every run: Lecture 6 can test gates one by one.
  • Its failures were narrow: one confident wrong decision (D4) on flash. On flash-lite: D4 again, a question without a “?” that ended the chat (C5), and a stock question it could not place (M9).

What it did not show, and what it cost

  • No never-events from the loop either. Lecture 3's tools already refuse closed centres, blocked codes and duplicate suppliers; they carried the safety.
  • The loop's misses were mostly unfinished work: an extra “confirm the registration” turn used up Kavita's answers (N6, N8, N9).
  • On flash-lite the loop passed 39 to the graph's 37.
  • More model calls, more seconds. Sampling the decisions in parallel would remove most of that.
  • The model's words can still be wrong: in C5 on flash-lite its question said “thirty thousand rupees” for an order Bahi would price at ₹24,072. Only the blocks written by code are guaranteed.
SoThe graph is not about a higher pass rate on easy cases. It moves the route out of the model's habits and into code you can read, test and change.

One graph, one model, many tools

Everything today was one agent: one control graph, one model, the tools of Lecture 3.

You would want a second agent only when a part of the job needs its own context (a 300-page contract to read), its own permissions (a finance user's tools), or its own clock (a job that runs for a day).

Even then, it is a node in the graph: called, waited for with an interrupt, its result read back like any receipt.

A quick test before you split
  1. Can the step be a tool? Then make it a tool.
  2. Can it be a node with its own prompt? Then make it a node.
  3. Does it need a different user, a different context window or a different lifetime? Only then, another agent.

A4 · The route for your module

A control graph, a router and a memory policy. Due before Lecture 5.

Build

  1. A route spec as data: spine, gates (named predicates, rules cited), asks, invariants.
  2. A LangGraph built from it, with a checkpointer and interrupts for every question and every wait.
  3. A router: one typed decision with a threshold.
  4. One more typed decision your module needs.
  5. A memory policy for the four levels, with one turn's context_for_turn().

Graded through

Route and authority (15): spec matches the graph that runs, never-events refused in code, approvals read back. Scenario pass rate (25), measured with logs. Tools (20): the router and decision with a measured confidence.

Guided track: copy route_spec.py and graph.py, rewrite the data. Builder track: generate nodes and edges from your spec, and test every gate combination.
