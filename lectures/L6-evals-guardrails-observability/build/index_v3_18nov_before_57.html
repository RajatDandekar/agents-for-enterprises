Observability Being able to answer a new question about what the system did, from the records it left, without running it again.

A trace: everything one turn did

The whole picture on the right of Argus is one trace. One message from Emma gives one trace.

It has an id. This one: . Every row carries it.
It has a shape. The first row is the turn. The rows under it are the steps of that turn, in order.
It has a clock. Each bar shows when that step ran, so you see where the time went.
Trace The record of one request from start to finish: every step taken to answer it, with times, tied together by one id.
Why not just logs? A log is a list of lines from the whole server. A trace is the story of one turn. For an agent, which takes a different path every time, the story is what you need.

A span: one row, one piece of work

Each row of the trace is a span. A span needs very little.

A name: what kind of work. “chat” is a call to the model; “execute_tool” is a tool call.
A start and an end: the bar. Its length is how long the work took.
A parent: the span it happened inside. That is why three rows are indented under the first.
Details: anything worth keeping about the work. What went in, what came out, the cost.
Span A record of one piece of work: its name, when it started and ended, and which span it was part of. Spans with the same trace id make a trace.

Click a pink row: one call to the model

The first “chat” row of our trace, opened. Tools call this a generation (Langfuse) or an LLM run (LangSmith).

What it is. We send text to the model and wait for its answer. That is one generation.
What went in. Much more than Emma’s question: the instructions, her saved memory and the list of tools go in on every call.
What came out. Here, no words for Emma yet. The model asked us to run a tool.
What it cost. Tokens are the units the model reads and writes (about ¾ of a word each). Cost = tokens × price.
Generation One call to a language model, recorded with its input, its output, the model’s name, the tokens used and the cost.

Click an orange row: one tool call

The model cannot read Ledgerline. It asks; our code runs the tool and hands back the result.

A tool span records a function our code ran because the model asked for it.
Arguments: exactly what the model asked for. Not what it said it asked for: what it sent.
Result: exactly what came back. The reply to Emma is written from this.
Why this row matters mostWords in a chat can be wrong and harmless. A tool call changes something: a stock check reads, but create_purchase_request writes. When an agent does damage, the proof is in a tool span’s arguments.

A score: a verdict attached to a trace

We just judged four turns by reading them. Write that judgement down as data, and a program can do it for every turn.

Score A name, a value and a comment, attached to one trace: commit_without_yes = true. A person can add one; a program can add one.
This is the bridge to Part 2A trace says what happened. A score says whether it was right. Once scores exist, you can count them, chart them, and block a change that makes them worse. That is an eval.

Where do the rows come from? Build one by hand

Three steps of work, one inside another. We wrap each in “start a record … end the record”.

1 · The work

Three nested steps

Handle Emma’s message.
  Inside it: ask the model.
  Inside it: call the tool check_stock.
2 · What gets written

Three records

ask the model · id b2 · parent a1
call check_stock · id c3 · parent a1
handle Emma’s message · id a1 · no parent
Each has a start and an end time.
3 · What you draw

A tree

handle Emma’s message
   ask the model
   call check_stock
Follow each record’s parent, and the list becomes the picture.
That is all a tracer does Note the time, note “who is running now” (the parent), run the work, note the time again, keep the record. About fifteen lines of Python.
The ids here are shortened for the slide; the notebook prints real ones. A finished child is written before its parent, which is why the turn comes last in the list.

What our fifteen lines lack

The idea is complete. Three practical things are missing, and each has a standard answer.

MissingA plain exampleThe standard answer
Agreed namesWe wrote “ask the model”. Another team writes “llm_call”. No tool can tell that both mean a model call.Shared names for agent work: chat, execute_tool, invoke_agent.
Somewhere to send itOur records live in a Python list. When the program stops, they are gone.One wire format every tool accepts, and a sender that runs in the background.
A screen to read itPrinting a tree is fine for 3 spans. Friday’s turn has , and there are thousands of turns.A tool that stores traces, searches them and draws them: LangSmith, Langfuse, Sentry.
The first two are one standardOpenTelemetry: an open standard for recording and sending traces. Almost every monitoring tool reads it. We use it; we do not write our own.

OpenTelemetry: the standard plumbing

An open standard for traces. You record spans once, in one format; any tool that speaks the format can show them.

We used opentelemetry-sdk 1.45.2. The same spans go to LangSmith, Langfuse and Sentry at once. OTLP is the name of the wire format; an exporter is the part that sends.

Agreed names for an agent’s spans

OpenTelemetry publishes a naming guide for AI systems (the “GenAI semantic conventions”). Three names cover almost everything we do.

The name on the spanIn plain wordsWhat travels with it
invoke_agent Ask Northbridgeone turn of the agentwho, which chat, Emma’s message, the final reply
chat claude-sonnet-5-5one call to the modelthe model’s name, what went in, what came out, tokens in and out
execute_tool check_stockone tool callthe tool’s name, its arguments, its result
Why names matterBecause the span is called chat and carries “tokens in”, LangSmith can show a cost, Langfuse can draw it pink and Sentry can add it to a chart. None of them needed our code. They only needed the names.
Status, Nov 2026: the guide is still marked “in development”, so a few names may change. The three above have been stable through 2026.

What an eval adds

Written down, repeatable, run every time

The inputs that matter, the criteria, a scorer that does not get tired, a threshold. Run on every change, many times.
Eval A test for behaviour that is not a fixed output: a known input, written criteria, a scorer (code, a model or a person) and a threshold that decides pass or fail.

An eval has four parts

Our task T02, “the usual: preview, yes, commit”, taken apart.

Before writing evals: read the traces

Error analysis, what practitioners do first: look at many real failures, name them in your own words, then count.

Why first: generic metrics (“helpfulness 4.2/5”) measure what is easy, not what breaks. The categories come from your traces. Ours did: our first suite run failed of runs, and we read every one.

Our first run, read failure by failure

Suite v1, 20 tasks: every failing check read in its trace, given a note, then grouped. Who was wrong?

The surpriseMost failures were the eval’s, not the agent’s: a judge cut off at 400 tokens, a task that demanded a preview when asking for the date was right, a judge that had not seen the memory. One was the agent’s: it worked out money itself.

Ragas: is the search behind the answer any good?

For a question about a rule, Ask Northbridge first searches the policies (Lecture 3), then answers from what it found. Two halves, two ways to fail.

MetricIt readsThe questionA low score means
Faithfulnessthe answer + the clauses foundIs every claim in the answer supported by those clauses?the model made something up
Context precisionthe clauses found + a reference answerAre the useful clauses at the top of the list?the search returns noise first
Context recallthe clauses found + a reference answerDo the clauses contain everything the reference says?the search missed a clause
Ragas An open-source library of ready-made metrics for search-then-answer systems, plus a few for agents. Each metric is a judge with a fixed recipe. We run it with Claude as the judge.
A reference answer is the right answer, written by a person who knows the policy. Writing references is the slow, human part. The three numbers then tell you which half to fix: the search, or the answer.

Ragas on our policy search, and on the agent

Four policy questions with references we wrote; then a planted fault; then two agent metrics on the two-turn order. From NB6d.

Read across a row. High recall, low precision: the right clause was found but sits under noise. High both, low faithfulness: the answer went beyond the clauses.
Plant a fault and see which number moves. A wrong answer should move faithfulness only; a wrong search should move precision and recall. A metric that does not move is not worth keeping.
Agent metrics. Tool call accuracy (code): an exact match with a reference list of calls. Good prompt , Thursday . Goal accuracy (a judge): good , Thursday . The correct run scored lower than the incident.
Why: the good run showed the preview twice before it saved (allowed), and an exact match scores three calls against a reference of two as 0. Thursday’s calls look like the reference list, which does not know they came before Emma’s yes. The judge was wrong about the good run. Ragas does not read Ledgerline: the end-state check still decides.

  3. 3A simulated conversation fails. Name three things that could be at fault.The agent, the simulated user, or the scorer (a code check or the judge). Read the transcript before you decide.
