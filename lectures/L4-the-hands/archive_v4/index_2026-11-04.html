Section 2 of 11 · Schemas
Last sectionThe model writes a request; our code runs it. Now: how does it know what to write?

How does a model know what to send?

Free text, or a contract?

The extremes again.

Free text

“check stock for the 500 Wh pack please”

Easy for the model to write. Our code must guess what it meant: which item, which warehouse. Every guess is a bug.
A full program

Let it write Python

Exact, but now our code runs whatever the model wrote. One wrong line and it is in Ledgerline.
The middle · a schema

JSON Schema

A small, standard description of the JSON we accept: the fields, their types, which are required. The model fills it in; our code checks it before anything runs.
Input schema · output schemaThe input schema is what the model must send. The output schema is what it gets back. Both live in the tool’s tool.json.

check_stock’s input, built up

Five clicks, five words of JSON Schema. The last one is the real file.

Six words cover almost everything

Each one shown on a real tool from our toolbox.

The tool folders in ledgerline/ledgerline/toolbox/. “format” is checked by our own argument_formats; the schema the model reads says only string.

What it gets back

The output schema describes the result, so a host can check it and the model can rely on it.

Every field in check_stock’s schema is in the real result, with the right type.

Four fields in the result are not listed. JSON Schema allows extra fields unless you forbid them. A finding, not a failure: we come back to it in Section 10.

Checked once, at the door

Before tool.py runs, ToolSpec.check compares the arguments with tool.json. A bad request never reaches Ledgerline.

Section 3 of 11 · Inside a tool
Last sectionA schema says what goes in and what comes out. Now: what happens in between?

What is inside a tool?

The toolbox

Each tool is a folder with two files: tool.json, what the model reads, and tool.py, what runs.

One tool per business activity: 8 read, 8 write. Every write previews first and commits only on confirm=true.

The same folders feed the chat, the MCP server, the Workflow Studio and the tools page.

ledgerline/ledgerline/toolbox/: 15 shipped folders and supplier_certificates, which we build in Section 4.
Identity. name is what the model calls; description is what it reads to choose.
For us, not the model. writes, version and the three Ledgerline services it uses.
input_schema: one required string. From Section 2.
output_schema: what comes back.
example and the MCP annotations: read-only, not destructive, safe to repeat. Then the timeout policy.
run(s, item_code): s is Emma’s Ledgerline session. The arguments are already checked.
Service 1, itm_get: does the item exist? What is its unit?
Services 2 and 3: the warehouse list, then stk_query for each warehouse.
Translate. Legacy column names become plain fields; free = on hand − allocated.
One clean result, with totals and days of cover across all warehouses.

Where the services are written down

Henrik Weber’s documentation from Lecture 3: 04_service_definitions/, one file per Ledgerline service.

Exported from Ledgerline’s service registry on 26 October 2026. The 38 purchasing definitions match the sandbox’s ledgerline/erp/services.py field for field (tools/northbridge_docs/verify_seed.py). Students: git clone https://github.com/RajatDandekar/northbridge-docs.

check_stock’s three services, as Henrik’s files define them

How do you build a new tool from scratch?

Step 1 · Start from the job, not the database

§6.2: lithium-cell parts need a supplier with a valid UN 38.3 certificate. Emma needs to check that before she orders.

The new tool: supplier_certificates. experiments/logs/new_tool_build.json, step 1.

Step 2 · Find the services in the docs

Search the 38 purchasing services for suppliers, certificates and items. Eight candidates.

Searched in Henrik’s documentation: 04_service_definitions/service_index.csv (one row per service: name, module, title, kind, screen, file), then the files in purchase/.

Step 2 · Read the three definitions we chose

Inputs: each needs one code, sup_cd or itm_cd. So the tool’s only required argument is supplier_code; item_code is optional.
Errors: ERR-SUP-0030 and ERR-ITM-0010 become ok=false with a next_step. sup_cert_get has none: an empty list means no certificate, un38_3: none.
Reads only: all three are kind: read, so the tool is read-only and safe to retry (idempotentHint: true).

Days left per certificate, and the best UN 38.3 as valid / expired / none.
One page of results, with total and next_cursor.
The §6.2 answer: with item_code, a third read; a next_step that says not to order.

Section 5 of 11 · The MCP standard
Last sectionSixteen tools in our own format. Now: Claude Code, Claude Desktop and our own app all want to use them.

Why does every app need its own plug?

Fig. 4. Every app that wants Ledgerline writes its own integration, and every new system multiplies them. With one protocol, each side is built once.

Three roles

Model Context Protocol (MCP)An open standard, from Anthropic in 2024, for how an app finds and calls tools on another program.

The host is the app with the model. It runs one client per server.

Our server, ledgerline-toolbox, is our 16 tool folders, bound to Emma’s session.

Fig. 5. The host decides what to call. The server only lists its tools and runs them.

JSON-RPC: a request, a reply, the same id

The first message our client sent, captured on the pipe. Four fields.

--tools check_stock serves one tool; --all serves all 16. --user binds it to one person’s Ledgerline session.

Section 10 of 11 · Production grade
Last sectionIt works on Emma’s order. Now: would it survive a year of real orders?

Is the toolbox ready for real orders?

Works once, or works every time?

A demo passes the happy path. Production is measured against criteria agreed with the client.

How each number was measured

On Modal, against the sandbox, every tool, before and after.

Schema · Reliability

Fuzzing

calls with wrong types, blanks, huge strings and nonsense quantities. Before: % were not business errors, and nonsense quantities were saved. After: 0 and 0.
Latency

Overhead only

Tool time minus Ledgerline’s own service time, calls through MCP: p99 ms against a 200 ms limit. The slowest is search_policy.
Timeouts

Injected faults

A busy server, an outage and a lost reply, on every service each tool calls: of tests pass. Reads retry twice; writes look themselves up.
experiments/production_grade.py → logs/production_grade_before.json, _after.json, merged in production_grade.json.

The one we fix live

A write is retried: a lost reply, or the model calls again with the date written differently. Does Ledgerline get two purchase requests?

Yes. “9 Nov 2026” then “2026-11-09” made two requests for the same 2,000 packs.

The idempotency key is built from the arguments as written, so a rewritten date is a new key.

The fix: rewrite the date at the door; look the document up after a lost reply.

Two small changes

The key says what the order is. The door makes sure equal orders are written the same way.

Plus, in receive_goods and send_message: after a lost reply, look the document up instead of returning TIMEOUT. Before: 6 duplicates. After: 0.

Right tool, right arguments, on five hosts

30 golden tasks. The same 16 definitions, discovered from tools/list.

Claude’s misses are all a read before a write (order_status before release or approve), not wrong arguments; first-call scoring counts them. logs/host_matrix.json.

Honest open items

Five criteria pass. These do not yet, and here is why.

Payload
list_my_approvals with 1,000 waiting was 167 KB; now capped at 50 rows (8.5 KB). But only supplier_certificates paginates. Adding limit and cursor to the five older list tools changes their schemas: a versioned 1.1 change.
Regression
All 8 write tools pass every case. 11 of 16 tools in all: the 5 read tools fail only on pagination, the item above.
Usability · MCP compliance
Under 95% on two hosts: Claude (API) 90% and Claude Code 93.3%. 12 of 16 tools are right on every host. Next: descriptions that say “no need to check the status first”.
Change management
Every tool has a version, published over MCP; 8 have release notes; rollback is a git tag. Client sign-off cannot happen in a sandbox: it is a process step with the client.
