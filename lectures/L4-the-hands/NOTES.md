Dr. Rajat Dandekar presents.

**The one idea.** A model only writes text. A tool is a function *our* code runs when the model asks; the model sees the
tool's definition and its result, and nothing inside it. Say it at the start, prove it in Section 8, use it everywhere.

**The rhythm** (Rajat's L2 rules): part slide → teach from the extremes → the section's own question (30 s, one line in
the chat) → the film, where there is one → 1–3 technical checks, answers on click. Three films (`tool`, `context`,
`orchestra`), never back to back. Films never autoplay: click play, or **Present** for full screen. Until a film lands
in `films/`, its slide shows a placeholder card: skip it and go to the check slide.

**Where the numbers come from.** `figdata.js` (window.L4), generated by `gen_figdata.py` from `experiments/logs/`:
`anatomy_check_stock.json`, `new_tool_build.json`, `mcp_raw.json` (+ `logs/wire/*.jsonl`), `our_harness.json` (the
full context at every model call, with the provider's own token counts), `claude_harness*.json` (+ `claude_runs/`),
`host_matrix.json`, `production_grade*.json`. Re-run `python3 gen_figdata.py` after any experiment.

**About the Claude Code runs (say it if asked, not on the slides).** Every Claude Code run is the real Claude Code CLI
(2.1.241, headless `claude -p`, stream-json) on our stdio MCP server, with the model **claude-sonnet-5.5**. The CLI on
the build machine was logged out (`claude auth status` → loggedIn false; logged as attempt 2), so the model calls went
through OpenRouter's Anthropic-compatible endpoint (`ANTHROPIC_BASE_URL`). Everything else (the harness, the MCP client,
the wire) is Claude Code's own. **To run it live in class, run `claude auth login` on the presenting laptop first.**

## 2 · Schemas from scratch (7:15–7:25) · 13–19

**13 · Part.**

**14 · Free text or a contract.** Free text: our code guesses [click]; a program: we run whatever it wrote [click];
the middle: JSON Schema [click]. Input schema = what it must send; output schema = what it gets back.

**15 · Input schema, field by field.** Five clicks: `{}`; type object; properties.item_code string; description ("a
prompt"); required. The last state is the real file. [click 5] Two real requests at the door: `{"item_code":"BAT-500"}`
runs; `{"item_code":500}` → "'item_code' should be string, got int.", 0 Ledgerline calls.

**16 · Six words.** type, required, enum (supplier_certificates' `un38_3`: valid/expired/none), format (our
`argument_formats` for need_by: date), description, examples. One click per row.

**17 · The output schema.** Every listed field is in the result with the right type. [click] [click] Four fields are not
listed (description, unit, free_total, on_order_total). JSON Schema allows extras unless you forbid them: a finding.

**18 · Checked once, at the door.** `ToolSpec.check`, four clicks: unknown arguments refused; types (with gentle
coercion: "2000" → 2000); our formats (positive, date rewritten as YYYY-MM-DD; this is Section 10's fix); required.
Right: real refusals, all with 0 Ledgerline calls.

**19 · Ask the class 3: why an output schema?** Hosts check `structuredContent` against it; other tools and code can
rely on it; tests can (Section 10 checks 603 ok results against them).
