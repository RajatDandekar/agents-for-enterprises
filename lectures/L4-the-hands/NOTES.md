## 2 · Schemas from scratch (7:10–7:18) · 13–20

**13 · Part.**

**14 · Free text or a contract.** Free text: our code guesses [click]; a program: we run whatever it wrote [click];
the middle: JSON Schema [click]. Input schema = what it must send; output schema = what it gets back.

**15 · Input schema, field by field.** Five clicks: `{}`; type object; properties.item_code string; description ("a
prompt"); required. The last state is the real file, with two real requests at the door: `{"item_code":"BAT-500"}`
runs; `{"item_code":500}` → "'item_code' should be string, got int.", 0 Ledgerline calls.

**16 · Six words.** type, required, enum (`un38_3`: valid/expired/none), format (our `argument_formats`, need_by: date),
description, examples. One click per row.

**17 · The output schema, field by field** (reworked: review point 2). Define it first: "a **promise** of what comes
back: for each field, its name, its type and what it means." Left: check_stock's real result for BAT-500. Right: one
schema field per click, its line lit on the left, ticked once seen.
[click 1] `ok` boolean: did it work; false comes with error and next_step. [click 2] `item_code` string, echoed back.
[click 3] `warehouses` array: one row per warehouse (on_hand, allocated, on_order, free). [click 4] `reorder_level`
integer. [click 5] `cover_days` integer: "days the free stock lasts at the usual daily use", all warehouses together.
[click 6] `below_reorder` boolean: a yes/no code can test. [click 7] Not in the schema: description, unit, free_total,
on_order_total. JSON Schema allows extras unless you forbid them, so nobody may rely on them: a finding for Section 10.

**18 · Who relies on it** (new). Three readers. The host: can check every result before the model reads it; our check
did this on 603 ok results in fuzzing, 0 violations (`production_grade.json`, Schema). [click] The model: names and
meanings; cover_days = 11 days for both warehouses, where Ledgerline's own replies said 9 and 2, one per warehouse
(`anatomy_check_stock.json`). [click] The next tool or our code: below_reorder is testable; supplier_certificates asks
for a supplier_code "from find_supplier": one tool's field is the next tool's argument (Section 9 uses exactly this).
[click] Without it: nothing to check against, so a broken result passes silently. With one, our check found a real slip
before the fix: create_purchase_order returned `warning: null` where its schema promised a string.

**19 · Checked once, at the door.** `ToolSpec.check`, four clicks: unknown arguments refused; types (with gentle
coercion: "2000" → 2000); our formats (positive, date rewritten as YYYY-MM-DD; Section 10's fix); required. Right: real
refusals, all with 0 Ledgerline calls.

**20 · Ask the class 3: why an output schema?** Now answerable from 17–18: the host checks results against it; the model
relies on names and meanings; the next tool and our code use a field without guessing; tests check it (603 results).
