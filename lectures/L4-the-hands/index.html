Section 2 of 11 · Schemas
Last sectionThe model writes a request; our code runs it. Now: how does it know what to write?

How does a model know what to send?

Free text, or a contract?

The extremes again.

Free text

“check stock for the 500 Wh pack please”

Easy for the model to write. Our code must guess what it meant: which item, which warehouse. Every guess is a bug.
A full program

Let it write Python

Exact, but now our code runs whatever the model wrote. One wrong line and it is in Ledgerline.
The middle · a schema

JSON Schema

A small, standard description of the JSON we accept: the fields, their types, which are required. The model fills it in; our code checks it before anything runs.
Input schema · output schemaThe input schema is what the model must send. The output schema is what it gets back. Both live in the tool’s tool.json.

check_stock’s input, built up

Five clicks, five words of JSON Schema. The last one is the real file.

Six words cover almost everything

Each one shown on a real tool from our toolbox.

The tool folders in ledgerline/ledgerline/toolbox/. “format” is checked by our own argument_formats; the schema the model reads says only string.

The output schema: a promise of what comes back

For each field: its name, its type and what it means. On check_stock’s real result, one field per click.

Three readers rely on it

And what goes wrong when there is none.

1 · The host

Checks each result

The app that runs the model can compare every result with the schema before the model reads it. Our check did this on real results: broke the promise.
2 · The model

Reads names and meanings

cover_days comes with “days the free stock lasts at the usual daily use”. So 11 means days, for both warehouses together. Ledgerline’s own replies said 9 and 2, one per warehouse.
3 · The next tool, or our code

Uses a field without guessing

below_reorder is a yes or no that code can test directly. supplier_certificates asks for a supplier_code “from find_supplier”: one tool’s field is the next tool’s argument.
Without itThere is nothing to check against, so a broken result passes silently. With one, our check found a real slip: create_purchase_order returned warning: null where its schema promised a string. Found, then fixed.

Checked once, at the door

Before tool.py runs, ToolSpec.check compares the arguments with tool.json. A bad request never reaches Ledgerline.

Is security done by the tool, or by guardrails?

Both. From first principles: a rule must live where nothing typed in the chat can switch it off.

In the tool · code

Rules that must never break

  • Identity: it acts as Emma, with her permissions and her £250,000 limit, never as an admin
  • A write: a preview first, then a yes
  • Nobody approves their own request
  • The door: types, formats, quantities above 0
  • Results capped; no secrets in them

Code runs every time, on every host. The model cannot argue with it.

In the harness and the prompt · guardrails

Judgement about words

  • Which tools each person sees
  • Ask for a missing fact; do not guess it
  • Stay on purchasing; be polite
  • Check the reply against the tool’s numbers (Lecture 7)

These need judgement. A model is good at that, and sometimes wrong. And a prompt stays behind in its own harness.

Our own runThe prompt said “never guess a code or a number”. The model still put a guessed date, 2027-02-01, into a preview. The preview, a rule in the tool, showed it before anything was saved. A prompt is a request; a tool is a wall.

Section 6 of 11 · MCP
Last sectionYour tools ran inside our harness. Now Claude, Claude Code and any other app want to use them too.

Why does every app need its own plug?

Fig. 4. Every app that wants Ledgerline writes its own integration, and every new system multiplies them. With one protocol, each side is built once.

Three roles

Model Context Protocol (MCP)An open standard, from Anthropic in 2024, for how an app finds and calls tools on another program.

The host is the app with the model: claude.ai, Claude Code, or our Ask Northbridge. Inside it, a client talks to one server.

The server is ours: our tool folders, bound to one person’s Ledgerline session. Your forge runs one for you.

Fig. 5. The host decides what to call. The server only lists its tools and runs them.

Your tools, at one address

All a builder needs from MCP: two questions every host asks, and an address to ask them at.

1 · “What tools do you have?”

tools/list

The server answers with each tool’s name, description, input schema and output schema: your tool.json, as the model will read it. Plus hints: read-only, destructive, safe to repeat.
2 · “Run this one”

tools/call

The host sends a tool’s name and arguments. The server runs it and sends the result back, with isError: true when it failed: your error contract.
3 · One address

A URL

The server on the network, over HTTP. Your forge has one. Any host that speaks MCP can use your tools from it, with no code written for that host.
That is allThe messages are small JSON requests and replies, a format called JSON-RPC. You read them by hand in NB4, section 5. The rest is plumbing that the MCP libraries do for you.

Three slips, and the tool fix for each

The tools returned the right numbers every time. The words around them were not always right.

1A guessed date (question 3)
It was already required, so Claude filled it in. Fix: the description says “ask the user if no date was given”, and the preview repeats the date for Emma to check.
2Pounds became euros (question 6)
No output says a currency: estimated_value: 273600. After Gdańsk and Eindhoven, Claude chose €. Fix: add "currency": "GBP" to the output schema.

Section 10 of 11 · Production grade
Last sectionIt works on Emma’s order. Now: would it survive a year of real orders?

Is the toolbox ready for real orders?

Works once, or works every time?

A demo passes the happy path. Production is measured against criteria agreed with the client.

1 · Schema: input and output validation

Threshold: · after the fix:

What it is

Every argument is checked against the input schema before the tool runs. Every result is checked against the output schema before anyone relies on it.

How we measured it

All tools have both schemas. We fuzzed every tool and checked all ok results against their output schemas: violations. Before: 1, the warning: null of Section 2.

In your forge

Production → Schema. Both schemas on every tool you switched on, one real call checked against the output schema, bad input refused at the door. Change the output on the Anvil and run it again.

For your own project

Write both schemas for every tool. In your tests, check every result with a JSON Schema validator (jsonschema in Python). One violation fails the build.

2 · Reliability: unhandled or non-business errors

Threshold: · after the fix:

What it is

When a call fails, it fails as a business answer in the error contract: ok=false, error, next_step. Never a crash, never a raw legacy code.

How we measured it

calls with wrong types, blanks, huge strings and nonsense quantities: % non-business, all in the contract. Before: %: bad dates reached Ledgerline, and quantities of 0 or below were saved.

In your forge

Production → Reliability. Wrong types, blanks, huge strings and nonsense numbers against your tools. Every failure must come back as ok=false, with what went wrong and what to do next.

For your own project

Fuzz every argument: wrong type, empty, too long, negative, out of range. Count anything that is not a business error. Aim for 0.

3 · LLM usability: right tool, right arguments, per host

Threshold: · after the fix:

What it is

Given a real task, does the model pick the right tool with the right arguments on its first try? Per host, because each model reads definitions in its own way.

How we measured it

30 golden tasks, the same 16 definitions, five hosts: our harness , Gemini , OpenAI , Claude Code , Claude (API) . Claude’s misses: a read first (order_status) before a release or an approval.

In your forge

Production → LLM usability. Golden tasks on your tools, the first model response scored. Make a description vague on the Anvil and run it again.

For your own project

Write 20 to 30 golden tasks from real requests, each with the expected tool and arguments. Run them on every host you support. Fix the descriptions, not the tasks.

4 · Latency: tool overhead, without the ERP’s own time

Threshold: · after the fix:

What it is

The time our tool adds on top of Ledgerline’s own service time. Ledgerline’s time is not ours to fix. Ours is.

How we measured it

calls through MCP: p50 ms, p95 ms, p99 ms, against limits of 50, 100 and 200. The slowest is search_policy, a search in memory.

In your forge

Production → Latency. It times your tools, with the sandbox’s own service time taken away.

For your own project

Time each tool with the service time taken away. Report p50, p95 and p99, never the average. Agree the limits with your client.

5 · Payload: response size and pagination

Threshold: · after the fix:

What it is

How big one result can get. Every list is capped and comes in pages, so one call can never flood the context.

How we measured it

list_my_approvals with 1,000 waiting: bytes; capped at 50 rows, with has_more: . But only 1 of the 6 list tools, supplier_certificates, takes a page cursor. Still open.

In your forge

Production → Payload. 500 extra rows, then every list tool: each must cap its rows and say how many more. Also: The Shield’s Scan my tools’ results for secrets.

For your own project

Load your system with ten times its rows. Call every list tool. Add a limit and a cursor; return the total and the next cursor.

6 · Idempotency: duplicate or retried writes

Threshold: · after the fix:

What it is

A retried write must not post twice: after a lost reply, or when the same order comes back written differently.

How we measured it

Before: duplicates after a lost reply and with the date written differently. After the fix: 0. Next slide: how we found it and fixed it.

In your forge

Production → Idempotency. A lost reply after the commit, then a retry; a retry with an argument written differently. It counts the documents in Ledgerline.

For your own project

Build the key from what the write is (the arguments, normalised), not from how it was written. After a lost reply, look the document up before you retry.

The one we fix live

A write is retried: a lost reply, or the model calls again with the date written differently. Does Ledgerline get two purchase requests?

Yes. “9 Nov 2026” then “2026-11-09” made two requests for the same 2,000 packs.

The idempotency key is built from the arguments as written, so a rewritten date is a new key.

The fix: rewrite the date at the door; look the document up after a lost reply.

7 · Timeouts: timeout and retry policy

Threshold: · after the fix:

What it is

Every call to Ledgerline has a time limit and a written rule for what happens next: reads retry, writes look themselves up.

How we measured it

A busy server, an outage and a lost reply, injected on every service each tool calls: of tests pass. The policy is now declared in all tool.json files.

In your forge

Production → Timeouts. A busy server, an outage and a lost reply, injected under your tools in a fresh sandbox.

For your own project

Write the policy per tool: the timeout, the retries, and what a write does after a lost reply. Test it against a fake service that is slow, down, or drops the reply.

8 · Regression: a fixed suite, run on every change

Threshold: · after the fix:

What it is

The same tests, run before every release: the happy path, validation errors, permission denied, pagination, retries.

How we measured it

of tools pass every case; all write tools pass. The 5 that fail are reads, and fail only on pagination (criterion 5).

In your forge

Production → Regression, or Run every check on my tools: all the checks as one suite. Run it after every change on the Anvil.

For your own project

Turn every bug you fix into a test. Run the suite before every release. Write tools: 100%.

9 · MCP compliance: the same tools on every host

Threshold: · after the fix:

What it is

The same definitions work on every host you promise: Claude, OpenAI, Gemini and our harness.

How we measured it

Every host accepted all 16 definitions. tools were right on every host; the approvals and the release (Claude reads first) and create_purchase_order (OpenAI, once) were not.

In your forge

Production → MCP compliance. It calls your own address over the internet, as Claude does: initialize, tools/list, tools/call, an unknown method. Section 7 was the live test.

For your own project

List the hosts your client uses. Run the golden tasks on each. Report per host and per tool.

10 · Change management: versions, release notes, rollback, sign-off

Threshold: · after the fix:

What it is

Tools change. Each change needs a version, a release note, a way back, and the client’s sign-off.

How we measured it

All tools have a version, published over MCP; have release notes; rollback is a git tag. Sign-off cannot happen in a sandbox: open.

In your forge

Production → Change management. Every knob you changed gives that tool a new version and a release note, published in tools/list. The sign-off stays with your client.

For your own project

Version every tool.json. Write a release note for every schema change. Tag each release so you can roll back. Get the sign-off in writing.
