The model writes a request

DefinitionFunction calling (also called tool calling): we send the model a list of tools; instead of words it may reply with a tool call, a small JSON request naming one tool and its arguments.

Part 2

Describing a tool

JSON Schema: how the model learns what arguments a tool takes, and how our code checks them.

A description of valid JSON, written in JSON

DefinitionJSON Schema: a JSON document that says what a valid piece of JSON looks like: its type, its fields, which are required, and which values are allowed.

Six basic types cover everything Kavita types:

string"GSK-SIL-05L", "PRD-07", "2026-11-09"
integer20000
number11.90
booleantrue / false (confirm)
object{ "item_code": …, "quantity": … }
array["item_code", "quantity"]
the smallest useful schema: check_stock's input 
{"type": "object",
 "properties": {
   "item_code": {
     "type": "string",
     "description": "Bahi item code, e.g. GSK-SIL-05L"}},
 "required": ["item_code"]}

Read it aloud: an object with one field, item_code, which is text, and must be there.

Kavita's request, as a schema

The file the model reads, from toolbox/create_purchase_request/.

Properties: each argument with a type and a description in plain words.

required: the four things Bahi cannot do without. A missing one is caught before Bahi is called.

confirm, a boolean: false by default means preview only. Part 4 explains why.

The description is a prompt: it is how the model knows when to use this tool at all.

Three more words

required: a list of property names that must be present.

enum: the only values allowed. Rohit's decision is "approve" or "reject", nothing else.

optional arguments are simply not in required; the tool's code picks a default. For every write tool, confirm defaults to false.

approve_purchase_request · input_schema 
{"type": "object",

   "request_no": {"type": "string",
                  "description": "e.g. PR/2026/04417"},
   "decision":   {"type": "string",
                  "enum": ["approve", "reject"],
                  "description": "approve or reject"},
   "comment":    {"type": "string",
                  "description": "optional note to the requester"}},
 "required": ["request_no", "decision"]}

How the model chooses a tool

It reads the names and descriptions, and nothing else. It cannot open tool.py.

In our round trip it had words, not a code. check_stock asks for a “Bahi item code”; find_item says “by description or code”. It picked find_item first. Correctly.

So write descriptions for a model: what it does, what it returns, when to use it, when not to. register_supplier says “only after find_supplier shows no existing match”.

find_item
Find stock items by description or code (e.g. '5 litre silicone gasket'). Returns active items, best match first, with code, unit and whether they touch food.
check_stock
Stock of an item in every warehouse: on hand, allocated, on order, reorder level and days of cover. (item_code: “Bahi item code, e.g. GSK-SIL-05L”)

Part 4

The tool contract

Six promises every Rasoi tool keeps, each shown on the sandbox with no model in the loop.

What makes a tool safe to hand to a model

  1. 1Typed inputs, checked once, at the door. (Part 2.)
  2. 2Errors that say what to do next.
  3. 3Preview, then confirm, before any write.
  4. 4An idempotency key: a retry never makes a second document.
  5. 5A receipt read back from Bahi, never assumed.
  6. 6The user's own permissions: the tool runs in their session.

Why a contract?

A model is a fast, tireless, literal new joiner. It will retry when unsure, skip a step when hurried, and believe whatever a screen says.

The contract puts Kavita's caution into the tool, so it holds whichever model, prompt or app is on the other side.

An error is the model's next instruction

Bahi speaks in codes for a trained clerk. A model reads every word you return.

So every failure returns ok: false, what went wrong in plain words, and next_step.

In the 30 tasks, Bahi refused 23 raw calls on flash; with the toolbox, 4.

Nothing is written until Kavita says yes

Every write tool takes confirm. False, the default, returns a preview and saves nothing.

The preview answers what Kavita would ask: ₹2,69,040 (₹11.40 old rate + Bahi's 18%), above her ₹2,50,000, so RMEHTA must sign.

Only confirm=true saves. The reply is a receipt with the real status: WAITING FOR APPROVAL.

Rohit approves from his own session. Kavita cannot: Bahi refuses her (ERR-SEC-0001).

The reply was lost. Try again?

DefinitionAn idempotency key is a label made from what the document is (who, supplier, item, quantity, cost centre, date). The same request always gets the same key.

We make Bahi save the order, then lose its reply: erp.inject("po_save", "timeout_after_commit"). 3,000 whistles from Sahyadri, ₹24,072.

Retrying a raw save makes a second order. The tool first asks Bahi "is there an order with this key?"

Count the orders in Bahi afterwards: two, or one.

logs/contract.json (idem_direct, idem_direct_raw). The key is a hash of the content, never uuid4() or the clock: a retry must produce the same key.

Three places in create_purchase_order

1. Make the key from the content.

2. Before writing, look for an order that already carries it.

3. If the save times out, look again before saying anything.

What we found: on the request path, a retry after a lost reply returns “Request PR/2026/04417 is not approved (status CL)”, because the request closes once its order exists. No second order is made, but the message is wrong. Also, a lost pr_save reply leaves the request in DRAFT on retry. Both reported to the lead as toolbox fixes.

create_purchase_request

Key first: has this exact request been raised?

Ask Bahi: the estimate, Kavita's limit, the budget. The tool never copies Bahi's rules; it asks.

Preview unless confirm.

Write, then the receipt read back: status, approver, next step.

def run(s, item_code, quantity, cost_centre, need_by, confirm=False):
    key = content_key("PR", s.user_id, item_code, quantity, cost_centre, need_by)
    for p in _bahi(s, "pr_search", raised_by=s.user_id)["rows"]:
        if f"key:{key}" in (p["remarks"] or "") and p["status"] != "RJ":
            return {"ok": True, "already_done": True, **_receipt(s, p["pr_no"])}

    rate = _bahi(s, "pr_fetch", itm_cd=item_code)["est_rate"]
    value = round(quantity * rate * 1.18, 2)    # Bahi estimates with 18% GST
    me = _bahi(s, "usr_get", user_id=s.user_id)
    budget = _bahi(s, "bud_check", cc_cd=cost_centre, amount=0)
    preview = {..., "estimated_value": value,
               "needs_approval": value > me["appr_limit"],
               "approver": me["manager_id"] if value > me["appr_limit"] else None}
    if not confirm:
        return {"ok": True, "preview": preview,
                "note": "Nothing has been saved. Show this to the user and ask to confirm."}

    pr_no = _bahi(s, "pr_save", cc_cd=cost_centre, need_dt=need_by, itm_cd=item_code,
                  qty=quantity, est_rate=rate, remarks=f"key:{key}")["pr_no"]
    _bahi(s, "pr_submit", pr_no=pr_no)
    return {"ok": True, **_receipt(s, pr_no)}   # read back: status, approver, next_step

Part 5

MCP: one plug for every app

The toolbox works in Ask Rasoi. How does it also work in Claude Desktop, the Workflow Studio, and whatever comes next?

Every app, times every tool set

Without a standard, each app writes its own glue for each tool set. 3 apps and 3 tool sets: 9 integrations, each with its own bugs.

With one standard plug, each app speaks it once and each tool set speaks it once: 3 + 3.

DefinitionMCP, the Model Context Protocol: an open standard for how an app discovers tools on a server and calls them.

Three roles

Host: the app the person uses. It holds the model and the conversation: Ask Rasoi, Claude Desktop.

Client: inside the host, one per server. It speaks MCP.

Server: lists its tools and runs them. Ours is bahi-toolbox, 15 tools, bound to one user's Bahi session.

The model still only writes tool calls. The host passes them to the right client.

The messages are JSON-RPC

DefinitionJSON-RPC: a tiny convention for calling a function on another program: send method and params with an id; get back the same id with a result or an error.

Every MCP session starts with initialize: the two sides agree a protocol version and say what they can do.

These three are the real first messages between our client and the toolbox server.

logs/mcp_wire.json, stdio session; server fastmcp 4.1.4, protocol 2025-06-18.

tools/list, then tools/call: the whole stdio session

Our client wrote these lines to the server's stdin and read its stdout. Click any line. The tools/list reply is 9,488 bytes: every tool.json, as MCP sends it.

What the host learns from tools/list

Each tool arrives with its name, description and inputSchema: our tool.json, unchanged.

And annotations: readOnlyHint is true for the 7 look-up tools and false for the 8 that write. A careful host asks the person before running a write.

A call returns content (text) and isError. A tool that does not exist comes back isError: true, “Unknown tool: 'no_such_tool'”. The host passes it to the model like any result.

The host turns each MCP tool back into a function-calling definition for its model. Same tokens: 1,912.

Same messages, two pipes

stdio: the host starts the server as a child process and writes one JSON message per line. For apps on your own computer.

Streamable HTTP: the server listens at /mcp; each message is a POST. The server gives a session id; replies come as JSON or a stream of events. For a web app like Ask Rasoi.

Ask Rasoi is a host too

Ask Rasoi does not import the tools. It discovers them: one client per server, the schemas from tools/list, each call a tools/call.

Add a server (email, a supplier portal) and Ask Rasoi gains its tools with no code change.

At the hands stage it takes one tool round per message: the model may call tools once, then it must answer.
