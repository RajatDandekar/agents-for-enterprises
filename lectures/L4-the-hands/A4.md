In Lecture 4 we gave Ask Northbridge hands. We opened `check_stock` line by line: a `tool.json` the model reads and a
`tool.py` that calls three of Ledgerline's legacy services and turns four `{rc, err_cd, msg, data}` envelopes into one
clean result. We built `supplier_certificates` from scratch in six steps, from Purchase Policy §6.2 to its tests. We put
the toolbox on an MCP server and read the raw JSON-RPC. We ran Emma's order on two harnesses, Claude Code and our own,
and saw exactly what the model read at every call: 1,555 tokens of tool definitions, the calls, the results, and nothing
from inside a tool. Then we measured the toolbox against ten production criteria and fixed one: a retried write with the
date written differently made a second purchase request (6 duplicates before, 0 after).

This assignment asks you to do the same for **one system in your own work or domain**. What we grade is a working tool,
real captured traces and honest measurements, explained in the terms of the lecture.

Use a system you know and are allowed to describe. Never paste real customer, patient or employee data, credentials or
internal hostnames: change names, and use a sandbox, a test tenant or made-up records. If you have no work system to use,
pick a public API you know well (a library catalogue, a weather service, a public transport timetable) and treat its API
reference as the service definitions.

## Part 1 · Build one tool from your system's service definitions (`TOOL.md` + a tool folder) · 3 points

Follow the six steps from Section 4, on one read-only tool first. NB4 exercise 3 (`payment_terms`) is the template.

1. **The job.** Two or three questions people in your domain really ask, who asks them, and why an existing tool or
   screen does not answer them. Say whether the tool reads or writes.
2. **The services.** Find the building blocks in your system's own definitions: an API reference, a WSDL, an OpenAPI
   file, a service catalogue, stored procedures. List the candidates you looked at, the ones you chose, and why. Paste
   one real definition (redacted) and one real raw reply, in the system's own envelope.
3. **The schema.** Write `tool.json`: `name`, `title`, `description` (at least 40 characters, written for a model that
   must choose), `input_schema` and `output_schema` (types, `required`, at least one `enum` or format if your data has
   one), an `example`, and the MCP `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`).
   Explain two schema decisions in a sentence each.
4. **The code.** Write `tool.py` with `def run(s, **args)`. It must return one clean result, not the legacy envelope:
   rename legacy fields, drop what the model does not need, and say in `TOOL.md` how many bytes came back from the
   services and how many the tool returns.
5. **The error contract.** Every failure returns `ok=false`, `error` in words, `next_step`, and the system's own code.
   Show at least four failure cases: one refused at the door (wrong type or missing argument), one refused by the system
   (not found, not allowed), one business answer that is not an error, and one of your choice.
6. **Tests.** At least the happy path and three failures as asserts. If your tool returns a list, it paginates
   (`limit` + `cursor`, as `supplier_certificates` does) and you test that the pages add up.

Load it next to the shipped tools with `add_tool_folder`, and paste the output of `lint_tool(name)` (it must be `[]`).

## Part 2 · Put it on MCP (`MCP.md`) · 2 points

1. **Serve it.** Start an MCP server with your tool. With the course server: put your folder next to the shipped ones and
   use `python -m ledgerline.toolbox.mcp --user <your user> --tools <your tool>`, or use your own server (FastMCP or the
   official SDK). Give the exact command.
2. **The raw wire.** Capture the JSON-RPC messages, as NB4 section 5 does with `stdio_wire`: `initialize` and its reply,
   `notifications/initialized`, `tools/list`, and two `tools/call`s, one that works and one with `isError: true`. Paste
   them, then point out in the messages: the protocol version agreed, your tool's `inputSchema`, `outputSchema` and
   `annotations`, and the `content`, `structuredContent` and `isError` of each result.
3. **Field by field.** A short table, as in Section 5: each MCP field, where it comes from in your `tool.json`, and
   whether your server sends it.

## Part 3 · The same task on two harnesses (`HARNESSES.md`) · 3 points

1. **Claude's harness.** Connect your server to Claude Code (`claude mcp add <name> -- <your server command>`) or Claude
   Desktop (`claude_desktop_config.json`). Ask one real question that needs your tool. Paste the transcript: every tool
   call with its arguments, every result, the reply. If you can, run it headless (`claude -p --output-format stream-json
   --verbose --mcp-config ...`) and report its turns, tokens and the cost it reports.
2. **Our harness.** Run the same question on NB4's harness (sections 6 and 7), or on your own loop: the model, the system
   prompt you gave it, the tools it saw. Print the context at every model call, with tokens per part, as `show_context`
   does. Say how many tokens your tool definitions cost and what share of the first call that is.
3. **Compare.** In a short table: tool calls, model calls, tokens in and out, what each model saw of your tool (and what it
   never saw). Then name **one rule you could enforce only in your own harness** (an approval gate, a tool list per user,
   a guard before writes, a loop limit) and say how you would build it.
4. **One model error.** Look for one thing a model got wrong while the tool's data was right (a guessed value, a wrong
   label like Section 9's "£273,600 ex. VAT"), or say plainly that you saw none in your runs. What would catch it?

## Part 4 · Production grade (`PRODUCTION.md`) · 2 points

1. **Pick five.** From the lecture's ten criteria (schema, reliability, LLM usability, latency, payload, idempotency,
   timeouts, regression, MCP compliance, change management), choose at least five that matter for your tool, and say in a
   line why the others matter less here.
2. **Measure them.** One number per criterion, with how you measured it, as Section 10 and NB4 section 8 do: for example
   output-schema violations on every result, the share of fuzzed calls outside the error contract, p50/p95/p99 of the
   tool's own time, the largest response in bytes, the pass rate on five golden questions per host.
3. **Find one failing, fix it.** Show the failing number, the change (code or `tool.json`), and the number after.
   If everything passes, push a criterion harder (more rows, a retried write, a timeout) until something fails.

**Builder track (optional).** Add a write tool with preview first (`confirm=false`), commit on `confirm=true`, an
idempotency key built from what the document *is*, and a receipt read back from the system. Show a retried call that
does not post twice.
