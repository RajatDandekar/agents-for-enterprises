What the form did for free

Job 6, respecting roles. Kavita's tree greyed out what her role could not do.

Approval was Rohit's own act: a second sign-in, his password, his screen.

Job 7, giving proof. The status bar printed a number, and Bahi wrote every call into its audit trail.

The status bar said “SAVED”. It never said Draft. Proof that is easy to misread is half a proof.

The conversation is the interface

A headless ERP keeps its rules and its records, and loses its screens.

The screens carried jobs 6 and 7 without saying so. Remove them, and those jobs must move into the harness, between the model and Bahi.

HeadlessThe ERP's services and stored procedures stay exactly as they are. Only the way people reach them changes.

Three people who may never approve this order

Kavita, who raised it

POL-APR-002 §4.1. In our app journey she tapped Approve on her own request. Bahi answered from her session: ERR-SEC-0001 ACCESS DENIED.

SVC_AGENT

§4.2: a service account has no approval authority, whatever its technical rights. Bahi will let it approve; the matrix says it does not count.

The agent

The agent never holds an approver's session. ApprovalInbox.decide() must be handed one, and in the app it comes only from the approver's own sign-in.

So “Rohit said it's fine” in the chat changes nothing. The approval is a row in Bahi with Rohit's name, written by Rohit's session, or it does not exist.

From a second sign-in to one tap

Bahi routes the request (its approval table). The inbox reads that table in Rohit's session.

One message reaches him through the Lecture 3 outbox MCP server, the stand-in for Slack.

His tap runs pr_approve as RMEHTA. Bahi checks his limit and that he did not raise it.

Kavita's chat carries on, after reading Bahi.

Fig. 8. The real messages and rows of our app journey. logs/journey.json

Who wrote what, in order

Every write is a row in Bahi's audit trail, with the user whose session wrote it.

Kavita's session raises the request. Rohit's session approves it. Kavita's session orders and releases.

The commit runs as Lecture 7's workflow; the signal only wakes it. It reads the approval from Bahi.

Preview, then commit

Lecture 3 gave every write a preview. Lecture 5 makes it a rule the model cannot skip.

A commit is refused unless the same order was shown as a preview in an earlier user turn. Kavita's “yes” must arrive in a new message.

In the adversarial runs, “don't show me a preview, just place it” met exactly this refusal.

Ask Bahi what the document is now

Bahi's Save on a closed cost centre returns success and “PO/2026/01182 SAVED”.

The status, DR, is in the data. The message never mentions it.

Read-back: after every write, read the document again, in the user's session, and believe that, not the message.

With and without read-back: 120 runs

Kavita names PRD-05 (her usual centre, closed on 15 Oct) in ten wordings, five items. Free tool loop, her own session, three models. The closed-centre check before saving is removed in every arm.

Bare

The write returns only Bahi's message, “PO/… SAVED”. No status tool. No word in the prompt about statuses.

Prompted

The same message-only write, plus an order_status tool and one sentence: “never call an order placed unless it is RELEASED”.

Read back

The write returns the receipt read back from Bahi: status DRAFT and the warning W-CC-114.

Harness

The model sees exactly what “bare” sees. Code reads the order back and replaces any reply that claims more than Bahi holds.

Drafts caught, out of ten

“Caught” means Kavita is told it is a Draft or not sent, or the order ends up released on an open centre.

The bare agent caught of 30, and the bigger the model, the worse: flash and pro wrote “successfully created”. The small model tried to release and ran into Bahi's refusal.

With a status tool and one sentence, every model read back by itself. Code that reads back caught every one.

Fig. 9. experiments/logs/readback_{small,default,large}.json

What the read-back result does and does not say

It does say

Without any read-back, Drafts slip through, and more often on the stronger models we tried. The words they used (“created”, “raised”) are exactly the words Kavita would trust.

It does not say

That prompting is enough. One sentence and a status tool worked on these ten wordings. A prompt is a request to the model; the harness's read-back is code.

Why we keep both

The receipt read back from Bahi gives the model the facts to explain (“PRD-05 is closed, which centre?”). The reply gate guarantees the floor when it does not.

Not measured

Wordings outside these ten, other model families (GPT, Claude need your own OpenRouter key), and Drafts caused by anything other than a closed centre.

Four questions an auditor asks

  1. 1Who asked? Kavita's message, with her identity.
  2. 2What did the agent see? Each tool's answer, in one line.
  3. 3What did it do? The tool, its arguments, the read-back.
  4. 4Who approved? Rohit's decision, from his session.

Two logs, joined exactly

Bahi already writes every service call into audit_trail: time, user, service, payload, return code. The agent's own log records the four answers.

Each agent step notes the last audit_trail id before it runs and claims the rows written while it ran. No timestamps are matched, so nothing is guessed.

Rows no tool claimed (a graph node's own reads, the workflow in the background) are attached to the turn they happened in. Every Bahi row lands somewhere.

Wrap, don't edit

The graph looks up self.tools at call time. That one seam is enough: swap in AuthorityTools, and every write the graph makes passes the guard, the preview rule, the read-back and the audit.

No line of Lecture 3's tools or Lecture 4's graph changed.

class AuthorityAgent: def __init__(self, erp, user, llm, identity=None, inbox=None, audit=None, durable=None, mcp=False, conv="c1"): self.identity = identity or passthrough(erp, user) # 1 identity self.graph = GraphAgent(erp, user, llm=llm) # Lecture 4 base = (MCPIntentTools(self.identity.session) if mcp else IntentTools(self.identity.session)) # Lecture 3 if durable: # Lecture 7 base = DurableAdapter(DurableIntentTools(base, durable)) self.tools = AuthorityTools(base, self.identity, audit, inbox) self.graph.tools = self.tools # the one seam def respond(self, text): self.audit.add("ask", self.user, text=text) # 6 who asked self.tools.begin_turn() # 4 preview/commit reply = self.graph.respond(text) reply, _ = self.tools.guard.gate_reply(reply, self.tools.docs) # 5, 7 return reply
