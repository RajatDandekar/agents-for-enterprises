Curriculum plan · AI Agents for Enterprises · Cohort 1

One legacy ERP, made AI-native, across eight lectures

Students follow one company through one product decision. Each lecture adds one layer of the harness to the same agent, and each layer fixes a failure they watched happen.

8 lectures · 16 live hours 31 Oct – 22 Nov 2026 · Sat & Sun 7–9 AM IST 1 reference system built first, end to end 8 domain kits for the capstone Single-agent architecture, own harness
01 · The spine

The case study

Kalpa Systems (working name, fictional) has sold Kalpa ERP to mid-size Indian manufacturers since 1999. It has about 400 screens, thousands of stored procedures and a loyal customer base. It is losing new deals to cloud ERPs that ship copilots. The board will not fund a rewrite. The brief: make Kalpa ERP AI-native without rewriting it. Our students are the team hired to do it.

The customer we test with is Ashoka Precision Components, a Kalpa customer. Its buyer Ananya (already on the marketing site) sends the request that runs through the whole course:

“Onboard Meridian Technical Services for our annual calibration contract. Then raise a purchase request for ₹2,40,000 against Facilities.”

That one sentence touches every hard part of enterprise agents: policy documents, master data, duplicate checks, approval limits, a write that can fail after it succeeds, and an approval that arrives two days later. Reusing Ananya and Meridian keeps the course continuous with the simulation students already played on the website.

No real client name, screen code, data or document appears anywhere. Every screen, service, procedure, policy and record is written by us. The real-world lessons are told as anonymised war stories.

Simplified: the service payload

Flat JSON, at most 12 fields, legacy-style names, and a one-page data dictionary. Students meet the naming pain without drowning in it.

Replaced: the activity XML

Each screen is a 30-line screen.yaml listing fields, tasks and the service each task calls. We show a realistic XML excerpt once in Lecture 3 (“this is what it looks like in the wild”) and then never again.

Kept: service-slot mapping, lightly

The draft document the screen holds becomes the agent's working memory: a typed dict of slots. Students see why it matters without building a slot registry.

L2

Answer from documents, act from the ERP

Sun 1 NovMarketed: Enterprise context: RAG + LLM Wiki

Buyers ask the copilot policy questions all day: “Can I raise a PR to an unregistered supplier?” “What is my approval limit?”

Concepts
  • Knowledge comes from retrieval; facts come from tools. Budget left and supplier status live in the ERP, never in a document.
  • RAG from first principles: chunking, embeddings, hybrid BM25 + vector search, reranking, citations.
  • LLM Wiki: ingest sources into linked Markdown pages with an index; retrieve by index and file search; update on change.
  • Context construction (part 1): what goes into the window each turn, and the token budget for it.
Build
NB2: The Kalpa corpus (user manual, procurement policy, onboarding policy, approval-authority matrix, two amendments) indexed both ways and exposed as one search_policy tool that returns citations.
Ablation
RAG vs Wiki on 40 questions: accuracy, citation precision, freshness after a policy amendment, tokens per answer, and a permission test with a confidential HR document. Five trap questions whose answer lives in the ERP show both approaches failing, which motivates tools.
Assignment
A2: RAG and Wiki over your domain's documents, a 20-question golden set with 5 traps, and a one-paragraph recommendation.
L3

From screens to tools

Sat 7 NovMarketed: Tools, APIs + Model Context Protocol · heaviest lecture

“Let the copilot onboard suppliers and raise purchase requests.”

Concepts
  • The tool-building process, six steps: inventory (screens → tasks → services → SPs) · live runs (record what the legacy UI really calls, with payloads) · cascades (what fires downstream) · variants (create, amend, approve; catalogue vs service) · screen state (preconditions and the draft the screen holds) · intent tool (one tool per business intent, variants as parameters).
  • Our own agent API: when legacy services are too tangled, write a thin façade over them. This is the answer to “alternatives to services”.
  • The tool contract: typed schema, descriptions written for a model, errors that say what to do next, dry-run preview, idempotency key, receipt.
  • Validate once: the ERP owns its commit rules; tools do not copy them.
  • MCP: one server, many hosts. Our Kalpa MCP server plus a marketplace MCP server (Slack or email) for notifications.
Build
NB3: Record live runs → draft tool specs → implement 8 intent tools → serve them over MCP → connect three clients: our harness, a marketplace host such as Claude Desktop, and n8n.
Ablation
Granularity on 30 tasks: about 38 raw services vs 8 intent tools vs one generic call_service. Measure success, tool calls, tokens and latency. Then the same 8 tools in a marketplace host vs our harness, which sets up Lecture 4.
War story
Anonymised: an LLM handed a 13-step process document tried to run 146 services. Students explain why after this lecture.
Assignment
A3: 5–8 intent tools and an MCP server for your domain, with the tool-level checklist filled for each tool.
L4

Who decides the next step?

Sun 8 NovMarketed: Orchestration: LangGraph + Jev

“It ran steps that didn't apply, and it skipped the certificate check.”

Concepts
  • A process document is a conditional flowchart, not a checklist. The control graph: one spine (understand → route → collect → check → preview → commit → confirm) with gated regions that default to skip.
  • Where code decides and where the model decides. Aim for mostly deterministic steps with the model at the edges.
  • LangGraph as the single agent's state machine: state, nodes, edges, checkpoints, interrupts for human input.
  • Jev for typed decisions (route the intent, classify an incoming document) with confidence, escalating when unsure.
  • Memory: working (the draft document's slots), session (checkpoints and compaction of long chats), user (Ananya's default cost centre), organisational (the Wiki).
  • Why one agent here, and when multi-agent would be justified.
Build
NB4: Turn the Lecture 3 agent into a LangGraph control graph, add the Jev router (recorded fixtures as a fallback) and a memory policy.
Ablation
Free tool loop vs control graph on 40 multi-step scenarios: wrong-step rate, skipped checks, tokens, latency. Jev vs an LLM router: accuracy, p50 latency, ₹ per 1,000 decisions.
Assignment
A4: The control graph for your domain's main journey (diagram and code), a router and a memory policy.
L5

A headless ERP with a human in charge

Sat 14 NovMarketed: Headless ERP + human approvals

The auditor: “Who approved this, and what did the agent see when it did it?”

Concepts
  • Headless ERP: the conversation is the interface; the ERP still enforces rules and keeps records.
  • Authority: the agent acts as the user, with the user's scopes, never as a superuser. The approval-authority matrix routes approvals.
  • A request is not a purchase order. Preview, then commit. Approvals are a separate authority.
  • Receipts and read-back: catch the silent failure where a save succeeds and the record lands on hold.
  • Audit trail and never-event guardrails as middleware.
Build
NB5 plus the reference app: chat UI ↔ agent API ↔ control graph ↔ MCP tools ↔ ERP, with an approval inbox on the web and in Slack, and an audit-log viewer.
Ablation
With vs without read-back on the silent-failure scenario. With vs without identity passthrough on an over-limit request.
Assignment
A5: Your domain agent end to end with approvals, on its four scenarios.
L6

How often does it fail?

Sun 15 NovMarketed: Evaluation + observability with Langfuse

Finance: “How often does it do this?” Nobody in the room knows.

Concepts
  • Evals before features. Derive the scenario suite from the control graph: every gate, every never-event, every variant.
  • Scenario types: single, composite, negative, adversarial, and multi-turn with a simulated user who leaves data out.
  • Deterministic metrics first: asked for the missing field, never asked for a field it could look up, no forbidden tool, no duplicate write, correct final status, right policy cited. An LLM judge only for tone and clarity, checked against 30 human labels.
  • Test the tests: run deliberately broken bots (too eager, asks too much, forgets) and confirm each metric catches its bot.
  • Observability: traces per node and tool, cost and latency per resolved request, p95, versioned prompts, tools and models, a regression gate in CI.
  • Model economics: a cheaper model on the routing and slot nodes, and the measured gap between our harness and a plain API call.
Build
NB6: A 60-scenario suite for the reference agent, the user simulator, the metrics, Langfuse dashboards and a trust scorecard.
Ablation
One large model everywhere vs a small model on routing and slot nodes: quality against ₹ per request. LLM judge vs deterministic metric: agreement rate.
Assignment
A6: A 30-scenario suite for your domain, the broken-bot check and a scorecard.
L7

Ship it, and survive Monday

Sat 21 NovMarketed: Deploy + recover with Temporal

“The ERP timed out after saving and the bot made a second PR. And approvals take two days; the bot forgot about it.”

Concepts
  • Where Temporal fits, answering your note: the commit-and-approval path of the control graph becomes a durable workflow. ERP writes are activities with idempotency keys. The human approval is a signal that may arrive days later. Reminders and escalation are timers.
  • Recovery: after a lost response, check the receipt before retrying.
  • Deployment: containers, secrets, environments, versioning, a rollout ladder (shadow → assist → partial auto → expand) with a kill switch, rate limits, a runbook, latency budget and caching. Development vs deployment.
Build
NB7: Temporal dev server in Colab and four failure drills: kill the worker mid-commit, ERP timeout after save, approval after 48 hours (time-skipping), double submit. The reference system goes live.
Ablation
Naive retry vs idempotent activity on 50 injected timeouts: duplicate documents created.
Assignment
A7: Your agent passes the four drills, with a runbook. Builder track also deploys it.

06 · Taken from your AI FDE talk

What “production grade” means in this course

The talk's four pilot failures (an untested question, a latency surprise, the harness-vs-API gap, the cost per question) become checks that the reference system has to pass. Students get the same two checklists for their capstone.

Tool level (L3, L5)

  • Typed input and output schema, validated
  • Description written for a model, with an example
  • Errors that tell the agent what to do next
  • Dry-run preview for every write
  • Idempotency key on every write
  • Receipt with the document's real status
  • Runs with the user's scopes, least privilege
  • Timeout, retry policy and rate limit
  • Lineage metadata: services and SPs it touches
  • Version number; changes are logged

System level (L1, L6, L7)

  • Pass bar and never-events agreed before building
  • Scenario suite with a regression gate
  • p95 latency per turn within budget
  • ₹ per resolved request measured and within budget
  • Harness vs plain-API gap measured
  • Every turn traced; every write in the audit log
  • Prompt injection from documents tested
  • Crash, timeout and double-submit drills pass
  • Rollout ladder with a kill switch
  • Runbook, and a status report of facts

10 · From your notebook

Your notes, answered

How much information should be exposed? Screen → task → service → SP.
Expose all four layers to students as the mental model, on one screen in L1 and as a method in L3. Expose to the agent only intent tools. The lineage travels as tool metadata, used for debugging, provenance and the “validate once” rule.
Expose a RAG layer to the chatbot? RAG vs LLM Wiki.
Yes, as one search_policy tool with citations. L2 builds both and compares them on accuracy, citations, freshness, cost and permissions. The trap questions teach the more important rule: documents explain policy, the ERP holds the facts.
How will tool building work? Services, cascades, live runs, variants, screen state.
Those five become the six-step process in L3 (adding the intent tool as the last step). Each kit contains exactly one or two of each, so every student practises every step.
A primer session for the overall goal?
Two parts. An async primer (L0) for LLM and ERP basics, and the first 30 minutes of L1 for the overall goal: the case, the scoreboard and the harness map.
Which aspects of harness design do we cover?
Context construction, tool interface, retrieval, control flow, memory, typed decisions, guardrails and authority, durability, and observability. Sub-agents are left out on purpose. See the harness map.
Context and memory management.
Context in L2 (what enters the window, token budget). Memory in L4 at four levels: working, session, user and organisational.
Do we really need LangGraph if the LLM orchestrates the tools?
Yes, used differently from the usual multi-agent demos. In L4 LangGraph is the single agent's control graph, and the ablation shows a free tool loop running steps that don't apply. That makes the marketed orchestration lecture strong instead of weak, and keeps your single-agent decision.
Jev is covered only if we build our own harness. Our MCP and the marketplace MCP.
Agreed. L3 runs the same tools in a marketplace host and in our harness; L4 adds what only our harness can do, including Jev routing. A marketplace MCP server (Slack or email) joins our own server in L3 and L5.
Blind spot: people expecting n8n multi-agent workflows.
n8n keeps a real role: the L1 workflow baseline and an MCP client in L3. L4 includes a “when to go multi-agent” segment. A one-line FAQ addition on the website sets expectations before the cohort starts.
Coverage: orchestration weak, evals weak, unsure where Temporal fits.
Orchestration now carries the control graph, Jev and memory. Evals get a full lecture of deterministic metrics, broken-bot tests and Langfuse. Temporal owns the commit-and-approval path, idempotent recovery and the crash drill.
Alternatives to services; build our own APIs; how tangled should dependencies be?
The agent API façade in L3 is our own API. The complexity budget fixes the tangle: two cascades, two variants, one precondition, one silent failure, one shared engine per module.
Don't lose the class in slot mapping and screen state; simplify payloads and the activity XML.
Flat payloads of at most 12 fields with a data dictionary; a 30-line screen.yaml in place of the XML; slot mapping reduced to the agent's working-memory dict.
Each student builds an AI-native ERP of their own. What about the capstone?
The capstone is that ERP: their domain kit, built up through A1–A7, presented on demo day against the website's checklist.
