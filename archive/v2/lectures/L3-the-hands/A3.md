# A3 · The Hands, for your module

**Lecture 3 · From Forms to Agents · Vizuara AI Agents for Enterprises**
Due before Lecture 4. Builds on A1 (your module's before story) and A2 (its manual).

In the lecture we built eight intent tools and an MCP server for Kavita's purchase order. In A3 you do the same for
your own capstone module (`ERP(modules=["<your module>"])`, one of `pur_amend`, `fin_payables`, `hr_leave`,
`sales_orders`, `svc_warranty`, `inv_transfers`, `travel_claims`, `legal_contracts`).

## What to build

1. **The six steps, written down** for your module's main screens:
   - **Inventory:** screens → tasks → services → procedures (from the service registry and your live runs).
   - **Live runs:** run `legacy.happy_path(erp)` and at least two of the kit's `TRAPS`; save `erp.live_run()` as JSON.
   - **Cascades:** for each write, what it sets off (diff the tables before and after, as in NB3 section 2).
   - **Variants:** the two paths through one screen, and which payloads Bahi refuses.
   - **Screen state:** the Fetch-before-Save rule (or your module's equivalent), shown failing and passing.
   - **Silent outcome:** the case where Bahi says "saved" but the document is not where the user thinks.
2. **5–8 intent tools**, in `bahi/modules/<your module>/tools.py` (builder track) or as configuration (guided track).
   Each one is a sentence-sized job in the user's words, not a legacy service renamed. At least one must be a
   **façade**: several services and screens behind one call, ending in a read-back.
3. **An MCP server** for your tools, bound to your module's speaker's session (copy the pattern of
   `bahi.mcp_server.build_bahi_server`), and a short script that lists and calls the tools through `MCPClient`.
4. **Your module's four scenarios**, run with `ToolLoopAgent` and your tools, with the scorecard.

## What to submit

- `a3/live_runs.json`: the recorded live runs (happy path plus two traps).
- `a3/tools.py` (or `a3/tools.yaml` on the guided track) and `a3/mcp_server.py`.

- `a3/A3.ipynb`: runs top to bottom in replay mode with no API key (cassette `A3_<your name>`), and shows: the tools

## The tool checklist (one row per tool in `contract.md`)

| # | Contract item | What we check |
|---|---|---|
| 1 | Types | Typed JSON schema; arguments checked once at the door, with a readable error |
| 2 | Errors that say what to do next | Every legacy error code your tools can hit is mapped to a `next_step` |
| 3 | Preview | Every write previews first (`confirm=false`) and commits only on `confirm=true` |
| 4 | Idempotency key | Writes carry a key derived from content (a hash, never `uuid4()`); a retry returns `already_done` |
| 5 | Receipt | Every write reads the document back and returns its real status, with a warning when it is not where the user thinks |
| 6 | Validate once | No business rule copied from a procedure into the tool; previews ask Bahi's own services |
| 7 | Permissions are the user's | Tools act through `erp.session(<speaker>)`, never the service account |
| 8 | Timeout and retry | Reads retry; a lost write is looked up by its key before anything else (test it with `erp.inject(svc, "timeout_after_commit")`) |
| 9 | Version | Each tool has a version; receipts carry it; the MCP server publishes it in `_meta` |

Also tick, per tool: the description says what it returns; the arguments are in the user's words; the services it
may call are listed.

## How it is graded

A3 feeds two lines of the /100 capstone rubric:

- **Tools · 20 points.** 9 for the contract across your tools (one point per item, all tools must meet it);
  5 for the two contract tests passing in your notebook (silent outcome reported as such; lost reply leaves exactly one
  document); 3 for the façade (several services, one call, a read-back); 3 for the MCP server listed and called.
- **Scenario pass rate · 25 points** (shared with later assignments): your four scenarios, never-events included.
  At A3 we record your baseline; the points are earned on demo day.

Late or not runnable in replay mode: the notebook part scores zero until it runs.

## Two tracks

**Guided track (configuration).** Describe each tool in `tools.yaml`: name, description, arguments with types, and the
ordered list of services it calls with the field mapping, its preview services and its read-back service. Use
`contract_audit()` from NB3 section 4 to check the static items. You still write the two contract tests.

**Builder track (Python).** Write the tools with the `@tool` decorator from `bahi.agent.tools` (give each a
`version=` and `services=`), raise `ToolError(what, next_step, code)` for every failure, use `content_key()` for keys
and a `_receipt()` of your own for read-backs. Write the façade by hand, the way NB3 exercise 4 does.
